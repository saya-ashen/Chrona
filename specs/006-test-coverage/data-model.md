# Data Model: Test Coverage

## Test Scenario

Represents one named behavior to verify.

**Fields**:
- `id`: Stable scenario identifier.
- `suite`: `core-flow`, `complex-graph`, `checkpoint-regression`, `recovery`, or `interface`.
- `priority`: P1, P2, or P3 from the feature spec.
- `preconditions`: Required workspace, task, plan, graph, provider, or UI state.
- `actions`: Ordered user or system actions performed by the test.
- `expectedOutcomes`: Observable states, results, visible messages, or layout conditions.
- `evidence`: Required diagnostics when the scenario fails.

**Validation Rules**:
- Every scenario MUST have a unique id and human-readable name.
- Every scenario MUST map to at least one functional requirement or success criterion.
- Every scenario MUST define expected outcomes before implementation.
- Failure evidence MUST be enough to reproduce or triage the scenario.

## Task Flow Fixture

Represents the baseline task-to-plan-to-execution journey.

**Fields**:
- `workspaceState`: Clean, seeded, or existing workspace baseline.
- `taskInput`: User request and task metadata used to create the task.
- `expectedPlanState`: Plan availability, graph validity, and user-inspectable plan summary.
- `executionPath`: Expected lifecycle progression.
- `terminalOutcome`: Completed, failed, blocked, or cancelled outcome and related evidence.

**Validation Rules**:
- Fixture MUST be repeatable across local runs.
- Expected terminal outcome MUST match the executed path.
- Fixture MUST not depend on hidden state from previous test runs.

## Plan Graph Fixture

Represents a graph under test.

**Fields**:
- `graphId`: Stable graph fixture identifier.
- `nodes`: Work, checkpoint, condition, retryable, blocked, or failure nodes.
- `edges`: Dependency relationships between nodes.
- `entryNodes`: Nodes allowed to start first.
- `checkpointResults`: Expected or malformed checkpoint result cases.
- `failureInjection`: Optional node failures or incomplete outputs.
- `expectedTransitions`: Expected state sequence for each important node.

**Validation Rules**:
- Graph fixtures MUST avoid accidental cycles unless the scenario is explicitly testing invalid graph handling.
- Valid graph fixtures MUST identify all prerequisites for each dependent node.
- Invalid graph fixtures MUST define the safe rejection or containment outcome.
- Checkpoint scenarios MUST define whether missing result data is expected to block, fail, or recover.

## Checkpoint Result Fixture

Represents review or decision output attached to a checkpoint node.

**Fields**:
- `checkpointNodeId`: Node receiving the result.
- `resultKind`: Approved, rejected, needs-changes, missing, malformed, delayed, or provider-specific fallback.
- `payloadShape`: Expected visible and internal result shape.
- `legacyErrorExpected`: Always false for supported checkpoint scenarios.
- `recoveryExpectation`: Safe next state when payload is missing or invalid.

**Validation Rules**:
- Supported checkpoint scenarios MUST fail if the legacy error text appears.
- Missing or malformed payload scenarios MUST produce safe blocked, failed, or retryable states.
- Result handling MUST not corrupt unrelated graph branches.

## Interface State Scenario

Represents one visible task workspace condition.

**Fields**:
- `viewport`: Desktop, mobile, narrow, short, or high-zoom equivalent.
- `workflowState`: Loading, empty, planning, executing, blocked, failed, completed, or retryable.
- `requiredVisibleElements`: Primary controls, status indicators, graph details, and progress messages.
- `requiredInteractions`: Pointer, keyboard, focus, or navigation interactions.
- `layoutRisks`: Overlap, clipping, hidden primary action, unreachable content, unclear status, or long text overflow.

**Validation Rules**:
- Every primary action MUST be visible or reachable in the tested viewport.
- Important status text MUST be readable and not clipped.
- Keyboard navigation MUST reach primary controls in a predictable order.
- Accessible names MUST describe primary controls and important status regions.

## Test Evidence

Represents diagnostic output captured for failed tests.

**Fields**:
- `scenarioId`: Scenario that failed.
- `expected`: Expected state or visible result.
- `actual`: Actual state or visible result.
- `visibleText`: Relevant user-visible text at failure time.
- `stateSnapshot`: Task, plan, graph, checkpoint, or execution state when available.
- `artifactRefs`: Screenshots, traces, logs, or reports generated by the runner.

**Validation Rules**:
- Evidence MUST identify the scenario without reading test code first.
- Product failures SHOULD include actual Chrona state or visible symptom.
- Setup failures MUST be labeled separately from product behavior failures.

## State Transitions

### Task Flow

```text
clean workspace -> task created -> plan generated -> execution started -> progress observed -> terminal outcome recorded
```

### Plan Graph Node

```text
pending -> ready -> running -> succeeded
pending -> waiting -> ready
running -> failed -> retryable -> running
running -> blocked
running -> failed
```

### Interface State

```text
loading -> empty
loading -> planning -> executing -> completed
executing -> blocked -> retryable -> executing
executing -> failed
```

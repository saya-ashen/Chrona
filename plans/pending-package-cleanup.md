# 后续包与应用边界清理

状态：待用户统一安排执行。本文件记录本轮讨论的后续事项，不表示已经实施，也不授权操作真实部署或数据。后续待办统一记录于此，不再写入历史保留审计 README。

## 1. 从 Chrona 主仓移除 memory-local（用户已明确决定，待执行）

`memory-local` 应作为独立应用模块维护，不应继续放在 Chrona 主仓组合中。移除主仓对它的内置携带和专属集成，保留其作为独立模块存在的可能；不将其功能搬进 kernel 或 Mind。

执行时核对并处理：

- 独立源码仓及其源码、锁文件、构建材料是否完整；保留独立应用源码，不将“移出主仓”等同于销毁该模块。
- 主仓 `resources/application-inputs/lock.json`、相应 bundle/artifact、恢复后的 `.generated/applications/memory-local`、默认应用选择或安装清单中对它的携带。
- 构建、发行、测试、文档及依赖锁中的专属引用；删除已无消费者的依赖和生成步骤。
- 不移除通用应用安装与工具调用能力，不为该应用保留特殊通道。

本项不删除真实 `memory.db`、用户偏好、部署副本或备份，也不操作正在运行的应用；现场卸载或数据处理另需具体授权。

## 2. 删除旧自动会话记忆接入链（用户已要求标记清理，待执行）

这套逻辑不是 Mind 的实现。当前 Web／MCP／QQ 会把聊天快照发送给所选记忆应用，调用 `conversation-context`／`conversation-retain`，注入上下文并按水位自动保存聊天文本。旧代码仍有消费者，不能按无静态引用直接删除；应连同业务调用一起移除，不再因“仍被调用”而保留旧机制。

处理范围：

- `packages/app-common/src/memory.ts`：旧记忆发现、快照、自动召回／保存及相关查询适配。
- `packages/app-common/src/preferences.ts`、`memory-settings.tsx`：旧记忆提供应用选择和自动开关；删除前区分是否有其他实际消费者。
- `conversations.ts`：记忆调用、提示词注入及专属 `MemoryJournal`、`memoryContext`、保存水位字段。
- `build/entry-conversations.ts`、`build/application-pages.ts`：相关复制／页面生成步骤。
- Web／MCP／QQ 独立源码中的对应工具、路由、设置页及专属测试，随后同步必要的构建制品和固定输入；不直接编辑恢复副本代替源仓修改。

保留现有聊天记录、执行、交付以及 Mind 的功能。无需把旧自动保存策略迁入 Mind，不处理真实历史聊天数据。

## 3. 收敛 logging（已调查的建议，最终归属待执行时落实）

先完成前两项，再按剩余消费者决定最小边界。

- `createLogger` 和 Pino 实现当前由 Server 使用，建议归入 `apps/server`。
- kernel、host、server 仍使用文本／对象／错误脱敏，必须保留所需行为；不能随旧记忆链一起删除，也不把整个 logger 并入 kernel。
- Pi 使用 `transcriptRedactor`，实际运行消费固定 vendor 副本；核对独立 Pi 的构建来源，避免删除仍是构建输入的源码。
- 删除 `summarizeText`（未发现调用）；核对并删除仅由测试直接使用的 `serializeSafeError` 包装，保留底层实际需要的错误脱敏。
- 移除 memory-local 与旧会话链后，重新核对纯文本脱敏复制步骤及 app-common 的 logging 依赖。
- 最终是否删除独立 `packages/logging`，以迁移后的真实消费者为据，不预留无消费者导出或包装。

- 删除仅验证上述退役行为的测试和文档示例；混合测试保留仍有效的断言。

### 保留与迁移

- 保留 `loadChronaRuntimeConfig`、`applyChronaRuntimeConfigToEnv` 及其必需类型和内部函数；保留现行 server、database、security 配置。

- 移动原有配置测试并保留有效场景：路径选择、缺失文件、文件值生效、显式环境变量优先、非法 JSON 和字段诊断；核对删除 web／experimental 字段后的明确拒绝行为。

- 不为本项运行 Nix 构建、不操作真实配置／数据库、不顺带合并其他路径工具。完成后报告实际删除、改名、验证和剩余问题。

- 远程设备已有设备 CLI、配对／轮询／报告／对账／模型路由、受监督 Pi 启动等源码，并非空目录或纯接口占位。未配置受审查 Pi 时，执行返回 `unavailable`，不启动模型。
- 用户明确当前没有实现远程设备功能，决定删除现有两个包；已有源码接线和测试不作为保留理由。后续若实现远程设备，应另行设计重做。

## 8. 收敛 apps/server：分离运行入口与 HTTP 职责（用户已要求记录，待统一执行）

- kernel 当前是库，由可执行入口创建并启动；保留库的形态。配置读取、数据库初始化、kernel／Host 组装、应用启动、tick 驱动和退出关闭仍需要入口承接。
- `packages/process` 只提供操作系统子进程的启动、监督、取消和停止证据，不负责应用登记、kernel 初始化或运行循环，不能替代上述组装入口。
- 当前 `chrona start → apps/server → kernel + Host + 数据库` 将必要启动代码与 HTTP 服务混在一起；后续可由 CLI 直接调用收敛后的启动代码，不因需要常驻运行就保留整套 Server，也不为拆分预先新增 runtime／daemon 包。
- 用户已明确不需要救援页面：删除 `rescue.ts`、静态页面、专属测试、自动启动监听器及发行资源引用；保留必要的 CLI 管理／恢复能力。
- Web 页面、浏览器登录及页面／API 转发按独立 Web 模块归属处理；Pi 工具桥接和配置接线与第6节一起迁移；远程设备路由与第7节一起清理。

- 完成职责收敛后再判断 `apps/server` 是否仍需独立存在、剩余 HTTP 入口如何组织；不把整体删除目录或保留统一 HTTP 服务作为预设结论。
- 验收覆盖启动、应用运行、tick 与退出关闭；同步 CLI、脚本、构建和测试入口。当前只记录，不改启动行为、不停服、不部署、不操作真实数据，不运行 Nix 构建。

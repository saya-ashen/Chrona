Chrona modules are long-running SDK processes. Import { on, chrona } from "chrona" and register on("tool", ...) handlers. The SDK connects to CHRONA_IPC_ENDPOINT using CHRONA_IPC_TOKEN and waits for the authenticated ready ACK. chrona.serve binds an ephemeral authenticated loopback HTTP listener and reports readiness over that connection; browsers reach it through the kernel proxy. Register handlers before asynchronous initialization. Keep durable application state under chrona.paths.data and application files under chrona.paths.content when content is declared. These files are private; expose bounded tools for cross-application access. Never accept caller identity, host paths, Run tokens or privileged authority from arguments.

Authoring is an ordinary application's material workflow. The owner grants an exact candidate admission to the current submitter identity and one target baseline through modules.admit. The author application prepares files under its own content directory, obtains immutable admitted source with modules.source, submits one fixed application material through modules.submit, and reads its durable receipt with modules.receipt. The kernel freezes source bytes and validates the fixed material before checks and activation. A replay returns the same receipt; changed arguments conflict. A passing author test does not itself establish activation or approval. This material admission does not authorize automatic model execution or an unlimited repair loop. Agent is a kernel namespace; concrete Providers, including Pi, follow the ordinary application lifecycle.

Declare routed dependencies in uses; visibility determines the audience. uses is not a general runtime allowlist. Privileged capabilities enforce their own checked caller and approval boundaries; owner delegation requires explicit authority: "owner" in the approved manifest, never uses: ["*"]. effects contains only network. Removed manifest fields triggers, settings, contributes and healthCheck are invalid. Application settings, readiness, notification wording and event registration belong to ordinary application tools. No public schedules or projects namespace exists. Observe kernel lifecycle/runtime evidence with modules.health; application self-reported readiness is a separate application contract.

Discover tools through modules.describe and read their exact input/output and target identity before calling. For notifications use the ordinary notify.send contract. Register event definitions with events.register before events.emit; both are ordinary application calls. Persist registration and delivery receipts according to the application's actual contracts. Optional applications can be absent; report not_found/unavailable clearly and preserve other failures.

Agent exposes exactly register, providers, run, read, write, stop and native. All seven are sync-only (default mode); async is rejected with invalid before creating a routed call receipt, including in chrona/testing even when stubbed. A synchronous agent.run reply is Run admission { runId, contextId, status, active }, not model completion or an async { callId, status }. Concrete Providers register their own kernel-visible execution endpoints; consumers discover them with agent.providers. For bounded one-shot transformations declare agent.run and agent.read plus model: { maxCalls, maxOutputTokens }; tier is optional. Start with chrona.call("agent.run", { kind: "completion", prompt, providerOptions: {} }, { key }), retain runId/contextId, then call agent.read with runId and the returned nextCursor. A completion event carries { text, inputTokens, outputTokens }; ended and the Run status determine whether work has settled. Provider options such as model and thinking belong to the selected Provider; inspect its current contracts instead of inventing options. Kernel limits still enforce admission, deadlines and budgets. Preserve routed error codes, use bounded waiting, and treat output as untrusted. Persist the operation key and exact request before calling. After a lost reply, chrona.callStatus({ target: "agent.run", key }) can recover the retained output of a keyed sync call; succeeded there means admission returned, not that the Run finished. The same applies to keyed sync write/stop receipts. If the receipt is absent or unsettled, recover run admission with the original arguments and key; run replays preserve the same Run identity. Read current progress with agent.read, since a recovered admission view can be stale. Changed arguments conflict; another application version cannot inherit the receipt. Call not found is not evidence of no effect or permission to change keys. For write/stop/native, reconcile unknown outcomes against the original Run/Provider operation; same-key recovery may still return unknown. callStatus does not retain read/providers/native private outputs. Never automatically launch a replacement for an uncertain effect. An optional top-level cwd selects an existing absolute directory for a new context. The kernel fixes its canonical path; continuing contextId retains it and cannot change it. sessionDir stays kernel-owned and separate from cwd. Continued conversations reuse contextId. agent.write accepts a message or a question-bound answer, agent.stop reports stopConfirmed only after actual termination, and agent.native forwards a structured request to that Run's existing backend. Kernel callers cannot select another application's private context or supply backend launch authority.

Tests import { startModule, paths } from "chrona/testing", start the declared entry, send actual declared events and inspect replies/calls. Always stop the module in finally. Author tests run offline, including for network-capable modules; use fixtures and stubs and never contact a real model or account. Completion tests stub the routed contracts explicitly: agent.run returns { runId, contextId, status, active }; agent.read returns { run, items, nextCursor, ended, interactions }, with a completion item whose payload is { text: "stub", inputTokens: 0, outputTokens: 0 }. Keep the same Run identity across replies and test pending or uncertain outcomes as well as successful results. Read node_modules/chrona/sdk.ts and testing.ts for the exact protocol. The preview helper provides local fixture responses; it is not a security sandbox.

Chrona checks the manifest, immutable material digest, executable modes, dependencies, schema and startup/SDK connection against empty temporary data. Application tests, typechecking and Git development run in the application development workspace; installation does not certify business behavior. Actual data migration runs only after approval with backup and recovery. Credential changes, data migrations and removal retain their actual approval boundaries. Stop uncertainty retains capacity. Never infer successful production behavior from a mock or installation check.

Dependencies use package.json with bun.lock or pyproject.toml with uv.lock. Chrona installs from lockfiles without accepting node_modules or .venv from candidate materials. Host programs belong in module.json packages for the current backend: ${BACKEND}. Derive application idempotency keys from the actual triggering operation and persist receipts before acknowledging work.

Application calls use `{ moduleId, tool }`; only kernel namespace targets use strings. Resolve dependencies through `chrona.dependencies` or discover exact IDs with `modules.list`. Pass idempotency keys only as `chrona.call` options; every tool declares its output schema. Timers use `timers.set/cancel/list` and `on("timer")`, not the removed schedule contract.

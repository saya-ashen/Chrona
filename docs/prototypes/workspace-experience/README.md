# Chrona 整体体验概念原型

**设计草案，非生产页面。** 2026-09-17。所有人物、工作、文档、时间和操作均为虚构；没有读取真实账户数据。

完整设计：[先看懂工作，再继续工作](../../zh/workspace-experience-design.md)。

## 打开

在 Chrona 仓库根目录运行：

```sh
python3 -m http.server 4178 --bind 127.0.0.1 --directory docs/prototypes/workspace-experience
```

然后打开 <http://127.0.0.1:4178/>。仅监听回环地址，不部署到公网，不需要登录。终端 Ctrl-C 停止。

本轮已启动临时预览进程 PID `1951496`，日志 `/tmp/chrona-experience-preview.log`；不是持久服务。若以后 PID 已改变，不要据此盲目停止别的进程。页面不能访问时，按上面命令重新启动即可。

原型状态仅在页面内存中：刷新或「场景与说明 → 重置整个原型」恢复初始样例。不会写浏览器持久存储，也不会把样例写入 Chrona。

## 建议先不读说明，直接试

首页优先掌握整体进展。导航仅 **总览 / 工作 / 日程 / 目标**。先尝试回答：

- 最近哪件事有变化？哪件只是没有新消息？
- 会议确认改期后，外部邀请有没有变化？
- 给报告写意见后，Agent 会不会自动收到？
- 第二版到来时，第一版是否还是已接受版？

如果必须看本说明才能找到动作，就是需要继续修设计的信号，不算用户使用错误。

## 可点击路径

### 1. 会议改期

打开「产品评审会」→ 比较两个时间 →「仅更新 Chrona 安排」→ 确认。

- 页面显示本地安排更新，外部邀请仍需跟进。
- 日程页使用同一个工作和更新后的本地时间。
- 「记录」显示决定及未做的外部动作。
- 「获取继续跟进信息」打开可手动复制的说明，**不发送**。
- 「场景与说明」可模拟建议过期；旧建议禁止应用。另一个场景按钮模拟取得新建议，仍需重新决定。

### 2. 阅读报告，反馈，接受新版本

打开「研究工具选型」→ 读第二版 →「写修改意见」→ 保存。

- 初始第一版已接受、第二版为最新。
- 建议写：补充试点负责人、验收时间与退出条件。
- 保存后明确「尚未通知外部 Agent」。可以取得继续工作信息，手动带回日常 Agent。
- 在页面顶端「场景与说明」选择 **模拟第三版到达**。这是原型控制，不是产品的 Agent 启动按钮；第三版文本是预写样本，不是根据意见生成。
- 新版到达不会自动切换阅读版本，也不会改变接受指针。
- 显式切到第三版 → 接受第三版 → 旧内容仍可读、工作仍开放、不自动成为目标正式材料。

### 3. 等待外部消息

打开「供应商资料核对」。看最后一次报告时间、当前未知和核查线索。没有伪造的进度条、远程暂停、重试或自动催问。

### 4. 托管执行的不同停止原因

打开「整理试点访谈」→ 选择输入范围 → 提交输入 → 模拟进入运行中 → 可暂停或确认取消。

通过场景工具另行模拟权限审批或失败：
- 权限审批明确展示路径、覆盖风险、本次范围与拒绝选项。
- 失败保留已完成部分；没有擅自新增引擎恢复行为。
- 本原型始终没有实际 Provider 调用或真实文件写入。

### 5. 其余入口

- 工作：筛选、标题搜索、记录新工作（仅内存）、查看记录。
- 日程：局部时间汇总与同一工作深链，不是完整周历原型。
- 目标：相关工作、成功标准、虚构正式材料阅读；不提供外部成果假晋升按钮。
- 场景工具：空工作区、读取中、读取失败、只读、过期冲突、恢复初始状态。

## 文件与实现边界

| 文件 | 用途 |
| --- | --- |
| `index.html` | 隔离入口、语义结构、CSP |
| `styles.css` | 概念视觉和三个屏幕尺寸的布局 |
| `prototype.js` | 虚构样例、内存状态、交互 |
| `checks.js` | 可选浏览器交互检查，不随页面自动执行 |

无 React、构建依赖、远程字体、CDN、API 请求、Service Worker、存储或计时自动推进。

CSP `connect-src 'none'`；禁止表单网络提交。仅加载同源静态 JS/CSS。内容中的可编辑文本转义后呈现。此安全收窄不构成正式结果文件预览沙箱实现。

这不是生产 UI 基础库。未来实现仍遵守 shadcn、i18n、pure model helpers、服务端权限及版本契约，不能把此 HTML 直接粘贴进产品取代它们。

## 已做的原型检查

2026-09-17，Chrome DevTools MCP，父代理直接操作本地页面，无子代理。

- `node --check prototype.js`、`node --check checks.js`：通过。
- 浏览器交互检查每个正式目标尺寸 **59 项通过**：
  - 1440×900：59/59。
  - 1024×768：59/59。
  - 390×844，移动设备模拟：59/59。
- 检查包括：四个导航、近况筛选、会议确认及记录、日程关联、反馈草稿、交接文字、精确版本接受、旧接受指针保留、外部未知、托管输入／授权区别、只读与过期禁止操作、创建文本转义、空／读中／错误页面、10 个页面无水平溢出、每页唯一主标题。
- 视觉观察：桌面总览、平板会议比较、手机报告阅读。不是仅以元素存在代替观察布局。
- 原生对话框：实测焦点进入、Escape 关闭、返回触发点。
- 移动验收后控制台 error/warn 为 0；观察到的页面资源全部来自本地同源。

### 保留的失败与限制

- 第一轮桌面检查在目标页发现两个一级标题：57 项通过后失败。修正为层级标题，再完整重跑，不把第一轮记作通过。
- 普通窗口 resize 到 390 时，Chrome 实际最窄为 500；那一轮 59/59 只是额外 500×844 检查，**不计作手机验收**。之后用设备模拟确认 `innerWidth=390` 并完整重跑。
- 切换移动模拟触发重载，可选检查脚本失效；首次调用报“runPrototypeChecks is not a function”。重新载入同一本地检查脚本后执行完成，非应用交互失败。
- Chrome 工具拒绝把原始检查输出保存到仓库路径（workspace-roots 限制）。未修改权限、未绕路导出原始证据；本节是根据工具返回撰写的检查摘要。截图在会话内查看，没有声称已保存截图文件。
- 未运行正式应用的 typecheck／全量 E2E：本次没有更改生产 TS/React、Schema、API 或运行逻辑。
- **没有**验证真实发送、Provider、持久化、权限隔离、文件下载、真实并发、完整屏幕阅读器兼容、百条工作规模，也未完成用户可用性验收。
- 原型的加载与冲突是显式模拟，不能证明生产服务正确处理这些问题。

## 后续验证

先让用户自己走一次上述路径，记录第一处停顿和误解。重点检查：

1. 新入口是否比原先「事项／任务／待处理」并列自然？
2. 「当前／记录」是否稳定好找？多份长期使用的成果是否需要独立常驻入口？
3. 整体进展的分组是否合适，还是更需要按目标分组？
4. 操作影响范围能否被准确预测？

获得具体反馈后再修设计。不能从自动检查通过推导用户已经理解或已经批准实施。

# v2-28 规格：心智 v2——关注清单与思考协议

状态：用户已确认方向（2026-11-01）；§9 第 1–3 步已实现并部署（2026-11-01，0.8.27）；第 4 步心智一侧已部署（0.8.29），应用一侧（calendar、planning）与第 6 步网页（线上为定制 web）已交由 Chrona 构建（2026-11-01），待用户审批；第 5 步待做。工具参数名为 kebab-case（`due-at`、`revisit-at`、`user-signal`、`wake-id`），存储与输出字段为 camelCase。依赖 [v2-26](platform-v2-26-mind.md)（心智）、[v2-23](platform-v2-23-app-pages.md)（模块设置）、[v2-25](platform-v2-25-contracts.md)（工具输出契约）。

## 1. 背景

v2-26 的心智是无状态的唤醒器：每次只拿一张快照问“要不要叫醒”，醒来的 Chrona 从零开始，靠记忆召回碰运气。上线首日（2026-10-31）的记录暴露了这些问题：

- 摘要不含当前时间与截止时刻；摘要哈希不变就不再判断，截止从 48 小时逼近到 2 小时不会触发任何判断。
- 不知道哪些事已处理、对用户承诺过什么；防重复靠醒来的 Chrona 记得写记忆、下次碰巧召回。
- 两次唤醒没有调用任何工具就回答“无事”；同样的输入另一次却核实并提醒了——摘要不足以判断，结果取决于它这次愿不愿意查。
- 唤醒提示由心智写，经 `provider.wake` 包成“模块输出（不可信数据）”，判断准则在信任模型里只是数据。
- 没有决策日志：直觉打了多少分、为什么没叫醒、叫醒后有没有用，都无法评估。
- “同一主题 30 天内不重复”与截止类事项的正常升级（提前、前一天、最后关头）冲突。

[steward-goals](steward-goals.md) §6 要求的是“持续跟进未结束的事……判断什么时候继续做、什么时候问用户、什么时候保持安静”。这需要心智**持有未完成的事**，而不只是看快照。

## 2. 原则

- **关注清单（agenda）是心智的工作记忆**：每条关注（concern）记录一件未完成的事的状态、截止、下次复查时间、对用户的承诺、用户的信号和升级梯度。心智、被心智唤醒的会话和普通聊天会话共用这一份清单。
- 心智仍然没有新权力（v2-26 §2）：它只读记录、维护自己的数据、叫醒 Chrona。醒来的 Chrona 做什么由现有策略与审批决定。
- **思考协议是可信指令，写在内核**：心智给的简报是数据；判断准则由内核在“心智唤醒的会话”里加入系统提示，心智（可被 Chrona 修改的模块）不能借简报注入指令。
- 直觉只决定是否叫醒、先看哪件；做什么由醒来的 Chrona 决定（沿用 v2-26 §10）。
- 每次判断与每次唤醒的结果都留记录，用于校准。

## 3. 关注清单

### 3.1 数据

心智数据目录下 `agenda.json`。一条关注：

| 字段 | 说明 |
|---|---|
| `id` | `c-<短 id>`，心智生成 |
| `title` | ≤120 字 |
| `goal` | 可选，关联的长期目标（≤120 字），如“2027 PhD 申请” |
| `status` | `watching`（盯着）· `acting`（Chrona 在推进）· `waiting-user`（等用户本人）· `waiting-external`（等外部，如推荐人）· `done` · `dropped` |
| `dueAt` | 可选，硬截止（ISO） |
| `revisitAt` | 可选，下次复查时间（ISO） |
| `escalation` | 截止类的提醒梯度：`none` → `early` → `day-before` → `final`，只升不降 |
| `commitments` | `{at, what}`，Chrona 对用户做过或答应过的事（最近 20 条） |
| `userSignals` | `{at, text}`，用户的表态：“已提交”“放弃了”“别再提”（最近 10 条） |
| `lastAssessment` | `{at, conclusion, by}`，`by` = `mind`（心智唤醒的会话）· `chat`（其他会话）· `user`（用户经网页/MCP） |
| `createdAt`、`updatedAt` | |

上限：未关闭的关注 200 条；`done`/`dropped` 关闭 30 天后清除。

### 3.2 工具

可见性 `provider`、`owner`（Provider 用 `m_mind_*`；用户经网页或 MCP 查看与修改）。

| 工具 | 作用 |
|---|---|
| `agenda` | 列出关注；默认未关闭的，`all: true` 含已关闭 |
| `note` | 新建（不带 `id`）或更新一条关注；可同时写结论、追加承诺或用户信号 |
| `report` | 心智唤醒的会话结束时报告结果：`wakeId`、`outcome`（`acted` 推进了事情 · `notified` 通知了用户 · `asked` 问了用户 · `nothing` 核实后无事）、一句话 `summary` |
| `decisions` | 最近的判断记录与 7 天统计 |

### 3.3 谁写

- 心智唤醒的会话：按 §6 协议，处理过的每条关注都要 `note`，最后 `report`。
- 所有会话（内核系统提示加一句）：用户交代要持续跟进的事、完成、放弃或改变一件事时，更新清单。用户说“WEHI 放弃了”，对应关注标为 `dropped` 并记下用户信号——心智就知道相关提醒是用户主动取消的。

## 4. 感知与信号

沿用 v2-26 §3 的读取与间隔。信号在 v2-26 四类之外，加上由清单得出的两类（每条有稳定 key，处理过不再触发规则）：

| 信号 | key | 条件 |
|---|---|---|
| 复查到期 | `revisit:<id>:<revisitAt>` | 未关闭且 `revisitAt ≤ now` |
| 截止逼近 | `due:<id>:<档>` | 未关闭且剩余时间进入 `<24h`、`<6h`、`<1h` 档（已过期为 `overdue`） |

摘要哈希包含每条未关闭关注的 `status`、`escalation`、剩余时间档与是否复查到期，不含 `updatedAt`；因此时间推移跨档、复查到期都会触发一次判断，醒来的会话写回结论本身不会。

### 4.1 应用的关注贡献（attention）

应用自愿把值得关注的事项交给心智（v2-14 `contributes`）：

```json
"contributes": { "mind": { "attention": "attention" } },
"tools": [{ "name": "attention", "visibility": ["provider", "owner", "modules"], "sideEffects": [], ... }]
```

- 工具无必填参数、无副作用，返回 `{ "items": [{ "id", "kind", "title", "at"? }] }`：`id` 为稳定标识（字母、数字、`_.-`，≤60），`kind` 为 `deadline`（须带 `at`）· `anomaly`（应用自身发现的异常）· `pending`（等用户处理的事），`title` ≤120 字；最多 20 条，只放此刻值得心智知道的。
- 心智每次感知调用 `modules.contributions({ section: "mind" })`，并行调用声明的工具（最多 10 个应用，各 10 秒超时）；失败或格式不符的应用列入上下文 `attentionUnavailable`，不阻塞感知。心智的 `uses` 只增加 `modules.contributions`；目标对模块可见即可调用，不要求 `uses` 列出目标（[安全机制简化 §3.2](security-simplification.md)）。
- 信号：`deadline` 按 §4 的档位得出 `app:<应用>:<id>:<档>`（`<24h`、`<6h`、`<1h`、`overdue`）；`anomaly`、`pending` 为 `app:<应用>:<id>`。规则兜底时 `<6h`、`<1h`、`overdue` 与关注清单的截止同样紧急。
- 上下文 `attention` 列出全部事项（`应用 · 类别 · 标题 · 时间`），随直觉 state 与简报发送；`minimal` 只发数量。事项标题来自应用，属于不可信数据。

## 6. 思考

### 6.1 简报（心智写，数据）

≤3900 字：`wakeId`、来源与直觉分数、主要关注、本次变化、关注详情（被选中与有变化的给完整字段：截止、状态、升级梯度、上次评估、最近 3 条承诺与用户信号；其余每条一行）、24 小时内日程等上下文、上次唤醒结论与 7 天统计。

### 6.2 协议（内核写，可信）

只在心智唤醒的会话（来源 `module`，模块为内置 `mind`）加入系统提示：

1. **先核实**：对每个变化和被选中的关注，用工具核对真实状态，不以简报为准；核实前不得认定“无事”。
2. **每件事回答四个问题**：真实状态与离完成还差什么；今天什么都不做最坏结果是什么、是否可逆；差的那一步谁能做（Chrona 在授权内能做就做；需用户本人做且用户已知、时间充裕就不打扰；需授权就发起审批）；下次什么时候再看。
3. **推进优先**：自己完成能做的一步 ＞ 通知用户 ＞ 什么都不做；能做掉的事不要变成提醒。通知须回答“发生了什么、为什么重要、建议做什么”，截止类按 `escalation` 只发当前这一级；非紧急并入日报；不确定时问用户，一次问清。对外可见的动作每次最多 3 个。
4. **看远一点**：同一故障反复 → 修复构建；同类手工劳动第三次 → 建议应用；目标长期无进展 → 提出具体下一步。未被选中的关注若明显需要处理，一并处理并在报告中注明“直觉漏判”。
5. **收尾**：处理过的每条关注调用 `m_mind_note`（结论、状态、`revisitAt`、新承诺、升级梯度）；事情完成或用户放弃则关闭并取消相关提醒。最后调用 `m_mind_report`，即使无事也要写明为什么、下次何时再看。

取代 v2-26 §5 的准则与“同一主题 30 天内不重复”：重复由关注的承诺与升级梯度判断；用户拒绝过的建议仍不再提。

### 6.3 每日回顾

每日 09:00 触发：过去 20 小时没有回顾、且有未关闭的关注或摘要有变化时，唤醒一次（来源 `daily`，计入每日唤醒上限）。简报标明“回顾”：逐条过一遍未关闭的关注，关闭已完成或已失效的，补齐缺失的 `revisitAt`，检查目标进展，必要时合并成一条日报。

## 7. 决策日志

心智数据目录下 `decisions.json`，保留最近 500 条。每次判断（摘要有变化或每日回顾）记一条：`id`、`at`、`trigger`、`source`（`intuition`/`rules`/`daily`）、`answer`（直觉原始分数，若有）、`wake`、`focus`、`urgency`、`changes`（信号 key）、`blocked`（超出唤醒限额时为真）、`outcome`（`report` 回填：`kind`、`summary`、`at`）。

7 天统计：唤醒次数、有效（`acted`/`notified`/`asked`）、无事、未报告。`decisions` 工具返回这些，网页与 MCP 可见。

## 8. 安全与成本

- 发给直觉服务的内容多了关注标题；`intuition-detail: minimal` 可关闭。设置说明写明。
- 关注内容由会话写入，可能含外部文本；简报整体作为不可信数据传入，协议在内核。注入最多导致多叫醒（受 v2-26 §4.3 与内核运行上限约束）。
- `report` 只记录，不触发任何动作。

## 9. 实现顺序

1. 决策日志；摘要加入时间、剩余时间档；`decisions` 工具。
2. 关注清单与 `agenda`/`note`/`report` 工具；清单信号；新的直觉 state 与 questions；新简报；每日回顾；`intuition-detail` 设置。
3. 内核：心智唤醒的会话加入 §6.2 协议；所有会话的系统提示加入维护关注清单的一句。
4. 各应用的 `attention` 贡献（§4.1）：心智一侧在内置模块实现；各应用一侧由 Chrona 自己构建加入（先日历与计划，再邮件与交易），经用户批准。
5. 每周校准：用决策日志统计误醒、漏判（用户主动提起而清单中没有）与被标“没用”的通知，提出阈值与心智自身的改进；按 v2-26 §7 删除反思。
6. 网页：心智应用页显示关注清单、今日判断与 7 天统计，用户可就地关闭或修改关注。

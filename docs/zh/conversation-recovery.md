## 修复范围

- 对话的执行状态与进度文字分别保存和展示。最终失败不能被前面的进度文字覆盖，刷新后仍应能看见失败。
- 用户显式选择继续时，以同一 Agent context 和新的持久请求键提交下一轮，先核对之前已完成与结果未知的操作。重复点击和丢失回复不能产生重复提交；运行中或停止未确认时不能继续。
- Pi 在同一次运行内进行有限原生重试，保留先前工具结果，不重新提交整轮任务。原截止时间、取消与工具预算继续生效。
- Author 的应用错误必须映射到 SDK 支持的错误码，避免无效错误回复被丢弃后等待到超时。

上述功能由入口应用、Agent/Pi 适配器和 Author 承担，不增加公开内核接口，不改变真实调用者、审批、预算或停止确认边界。

## 实现细节

### Pi 原生有限重试

针对 minimal 资源或指定模型的执行，在启动前创建一次性的私有设置目录，保留现有偏好并设置 `retry.enabled: true`、`maxRetries: 2`、`baseDelayMs: 2000`、`maxAgentDelayMs: 8000`、`retry.provider.maxRetries: 0`。Pi RPC 只切换 enabled，次数与延迟上限必须在启动前写入设置。每次瞬时故障最多两次原生恢复，通常等待 2 秒、4 秒；没有外层 Run 或 prompt 重放循环。原截止时间、取消、空闲超时和累计工具预算仍限制整次执行。

失败的 `auto_retry_end` 保留终态错误，包括没有 finalError 文字的情况。自动压缩继续关闭，模型身份校验不变。配置文件采用 0600 权限，结束后清理一次性目录；原配置文件不修改。

### Author 错误回复

实际 Hono → 路由 → supervisor → SDK 测试在原代码上复现了 60.38 秒超时：文件工具立即抛出 `source_io`，但 Author 将这个应用内部错误码直接发送到 SDK，接收方拒绝无效回复后继续等待事件截止时间。

Author 现在将 `unsafe_source` 映射为 `invalid`、`source_io` 映射为 `failed`；缺失路径直接返回不含宿主路径的 `not_found`。`list` 支持空字符串和 `.` 公开根目录别名，只列出真实存在的 sources/packages，不创建目录或暴露私有数据。其他授权与文件边界不变。

共享通道对其他应用无效回复的处理、普通模块调用的独立 deadline 传递仍是相邻问题；本次修正 Author 的错误来源，没有调整共享超时或放宽错误协议。

### 对话恢复的证据范围

Agent context 的 get 输出目前不包含保存的 Run error，因此界面持久展示执行失败及“执行接口未提供详细原因”，不会把推测写作实际原因。进度文字单独标记为过程，不能代表完成。继续处理要求用户显式操作，复用原 context，以固定请求身份创建下一轮；丢失受理回复后，刷新页面保留“核对继续请求”，不会由轮询自动重新提交。

### 丢失受理回复后的手动核对

普通消息与继续请求均在调用 Agent 前保存完整参数及固定请求键。刷新和轮询只读状态：普通消息显示“核对消息请求”，继续请求显示“核对继续请求”。用户点击后复用已保存的原始参数与请求身份；工具目录变化不会改变待核对请求。已取得运行回执时重复核对直接返回原结果，不创建新运行。尚未取得真实 Run ID 的消息不提供停止按钮。

已确认 finished 但最终 transcript 暂时读取失败时，界面显示“正在读取回复”，不把缓存进度或空回复当成完成结果。持久状态写入先于回复投递；真实 active、unknown 或停止未确认继续阻止下一轮。

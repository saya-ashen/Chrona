# 普通应用的本地桌面窗口

Chrona 的普通应用可以在运行 Chrona 的宿主桌面上打开窗口。应用仍用 `module.json` 声明入口、工具和依赖，经过原有候选检查、审批和版本激活；窗口内容、打开策略和工具包由应用负责。浏览器从其他机器访问 Chrona，不会把窗口转移到那台机器。

内核不增加桌面应用类型、窗口服务或数据表。原生程序和显式解释器入口继续使用现有对象入口；SDK 应用也可以启动自己维护的窗口子进程。窗口进程必须留在受监督的后代树中，由现有应用停止机制回收。

## 宿主桌面会话

Linux 宿主适配器将当前宿主的 `DISPLAY`、`WAYLAND_DISPLAY`、`XAUTHORITY`、`XDG_RUNTIME_DIR`、`DBUS_SESSION_BUS_ADDRESS` 传给应用。只有实际存在的值才传递；应用参数不能覆盖这些宿主来源。没有图形会话时，普通无界面应用仍可运行，桌面应用应返回明确的不可用结果。

这要求 Chrona 进程本身位于所需用户的桌面会话中。用户服务需要在启动前接收明确列出的会话变量；从 SSH、系统服务或其他账号启动时，不能由内核猜测显示器、用户总线或认证路径。详见[桌面会话启动说明](desktop-session.md)。

## 应用实现与交付

一个常驻 SDK 入口可以处理 `open`、`close`、`status` 工具并直接维护窗口子进程。重复打开应复用已有窗口；焦点操作是否被桌面允许需要单独报告。用户关闭窗口后，应用入口可以继续响应工具，允许再次打开。应用停用、更新或 Chrona 停止时，所有窗口后代都必须退出。

`chrona.exec` 等待程序退出，默认有 60 秒超时，适合有限任务；常驻窗口应由应用维护进程生命周期。依赖哪个宿主工具包、如何编译、界面如何呈现，属于应用自己的构建和运行材料。

[桌面示例](../../examples/desktop-demo/README.md) 使用常驻 Bun SDK 入口维护 Python / GTK 4 子进程，提供 `open`、`close` 和 `status`。构建会记录显式源码、运行产物摘要、工具链和宿主依赖；示例不会在启动时自动打开窗口。

Author 使用现有源码和产物流程：当前 Agent 在任务工作目录构建和测试，再通过显式源码清单与产物清单导入。保留源码、依赖锁、构建脚本和 `.gitignore`；对运行二进制记录实际摘要和执行属性。宿主系统工具与 GUI 运行库需要预先可用，Author 不安装桌面环境或编译器。详见[版本材料说明](author-version-materials.md)。

## 验收边界

以下事实分别保留证据：

- SDK 已连接，只证明应用入口可通信。
- 窗口工具包报告映射，只证明收到对应工具包事件；真正出现在宿主桌面还应有桌面窗口列表或人工检查。
- 窗口进程成功启动，不证明窗口出现或获得焦点。
- 用户关窗后，入口仍可响应状态并重新打开。
- 停用和更新需要实际后代停止证据，不能用已发送信号或已关闭 IPC 代替。

# Chrona 整体体验设计提案：先看懂工作，再继续工作

> 2026-09-17 · 设计草案 v1，待用户试用评议。不是已批准实施方案，不代表线上能力变更。
> 用户已选：整体进展优先；设计全产品、分阶段落地；可点击概念原型＋说明。
> **后续反馈：本轮仍像面向专业用户的软件，未通过易用性评议。** 用户要求具体页面与直接书写优先、复杂功能按需打开。新的配电脑场景参考见 [第二轮页面](../prototypes/pc-planning/README.md)。下面的四入口与“当前／记录”是保留供对照的 v1 提议，不是已确认实施方向。
> [第一轮离线原型](../prototypes/workspace-experience/index.html) · [原型操作与验证](../prototypes/workspace-experience/README.md)

## 1. 先纠正问题定义

用户的反馈不是“不够好看”，而是“打开之后完全无法理解每个部分的作用”。现有演示暴露了三个结构问题：

1. **入口要求用户懂内部分类。** 同时出现“事项工作台、任务、待处理”，用户要先判断自己处理的是哪一种对象。
2. **数据模型占据内容的位置。** 四种独立状态、下一步、来源、变更建议、成果状态与审阅各自成为醒目的模块；看到的是一组状态，不是“这次会议现在怎样”。
3. **有记录不等于能继续工作。** 用户看到回执、版本和反馈框，却未必知道点击后会改变什么，Agent 是否会收到消息，以及下次从哪里继续。

这些底层区别是必要的；问题在于把每一种区别都变成同等重要的页面模块。上轮测试证明了功能与适配，不证明可理解性。

**本次主张：把完整模型保留在系统里，把当前有用的判断放到界面上。** 不能靠删掉安全边界，或增加更多解释框，换取表面简单。

## 2. 产品心智模型

### 用户需要记住的只有三件事

- **工作**：我正在推进的一件事。会议、研究、写作、由 Chrona 执行的任务都在这里。
- **记录**：发生了什么、谁报告的、我做过什么决定。换会话或换 Agent 后可以接上。
- **成果**：值得阅读、审阅、使用的产物。它属于某件工作；稳定复用的正式材料可以属于目标。

“工作”是面向用户的统一入口，不是新增一个与 Task 并行的数据库对象。“事项”仍可用于自然语言，不再作为用户必须分辨的第二套任务类型。

**Chrona 的角色是共同工作的记忆与交接点。** 人和不同 Agent 可以在别处完成工作；Chrona 负责让状态有来历、产物可审阅、下一次接手有上下文。它不是必须打开的另一个聊天窗口，也不是声称控制所有 Agent 的驾驶舱。

### 不采用的整套范式

| 路线 | 不直接采用的原因 | 可以借鉴的局部原则 |
| --- | --- | --- |
| Notion 式空白页面＋数据库 | 用户还要自己搭建工作方法，默认入口不回答“现在怎样” | 内容优先、安静的文档阅读 |
| Linear 式统一状态流 | 等待来信、参加会议、接受报告并不共享一条工单状态机 | 列表扫描效率、稳定的位置和键盘操作 |
| 聊天作为首页 | 再次翻对话找决定；并取代用户已有 Agent | 不复制聊天，只保留可继续的上下文 |
| 全局审批收件箱 | 只能看见需要点按钮的工作，看不见长期等待和已交付产物 | “需要我”作为视图，而不是整个产品 |
| 控制台／监控大屏 | 对外部 Agent 的可观测性有限，百分比和旋转图标容易说谎 | 真正托管运行保留真实运行控制 |

这是基于 Chrona 工作形态的组合设计，不以复刻某个软件为目标。

## 3. 四个入口，一套工作身份

推荐主导航：**总览 / 工作 / 日程 / 目标**。设置和连接管理留在次级区域。

| 入口 | 用户要解决的问题 | 刻意不放什么 |
| --- | --- | --- |
| 总览 | 最近有什么变化，各件事现在怎样 | 任务总量 KPI、全量事件流、默认审批墙 |
| 工作 | 找到某件事，继续处理它 | 分开的外部任务和内部任务库 |
| 日程 | 哪些时间已被安排，有什么待确认变更 | 把时间块伪装成通知；把提议时间当已确认 |
| 目标 | 为什么做这些工作，已沉淀什么，缺什么 | 用任务完成比例代替目标达成；自动收纳所有附件 |

- 原“事项工作台”和“任务”在导航层逐步归入“工作”，底层 ID 与已有 URL 保留。
- 原“待处理”的能力归入“需要我”过滤与相关工作页；过渡期保留旧入口和深链接。运行中的输入／权限审批必须始终能发现。
- 不新增一个全局成果库，把成果与工作背景拆散。先在工作中找成果，在目标中找正式材料。跨工作搜索作为后续能力评估，不在本轮承诺全库索引。
- **统一外壳不等于统一后端成果存储。** 旧 Run 成果仍走真实旧适配器，独立成果走 TaskResult；尚未收敛的操作不能用 UI 假装已经支持。

## 4. 总览：整体进展优先，不是待办清零

### 默认首屏

1. 日期＋“工作总览”，一行从事实得出的近况，不是 AI 必须生成的日报。
2. **最近有变化**：结果交付、日程变更、真实阻塞解除。每行只讲一个变化及其来源。
3. **继续关注**：没有新交付但仍在推进／等待的工作，明确最后获知时间。
4. **最近收尾**：有明确结束状态的工作。不把“已接受一个版本”算作已结束。

不用四张数字卡占据整个首屏。可见数字只帮助定位，例如“需要我 3”，不把它变成主轴。

### 工作行的阅读顺序

`标题 → 一句具体近况 → 谁／何时报告或系统实际状态 → 自然进入内容`

例如：

- 「研究工具选型」第二版补充了部署成本；第一版仍是已接受版本。Pi · 40 分钟前提交。
- 「产品评审会」明日会议收到改期建议；原安排仍为 14:00。Pi · 25 分钟前记录。
- 「供应商资料核对」最近一次消息说还缺报价；当前进展未知。外部 Agent · 两天前报告。
- 「整理试点访谈」需要选择分析范围，托管执行已暂停。Chrona 执行状态 · 等待输入。

不能把前两行、第三行和第四行都压成“进行中”。也不在每行重复四种状态标签。

### 规模与排序

- 原型只有少量虚构工作，不能作为百条工作性能与检索验证。
- 生产总览每组有上限和“查看全部”，总量从完整查询得出，不从当前页凑数；支持分页和保留筛选。
- 最近变化依据有意义的记录时间，不把心跳、令牌使用时间当新进展。
- 需要我：真实输入／权限审批、待审阅变更、需用户处理的结果／反馈状态；不能仅凭一段 Agent 文本自动授予操作权限。
- 一个工作只出现一次主要列表行，同时有多个问题时注明“另有 1 项待处理”，不能被一个主状态遮掉。
- 不同读取来源有时间差时展示更新时间；不把局部读取失败渲染成空工作区。

## 5. 工作页：稳定骨架，内容随事情改变

### 固定骨架

1. 返回入口、工作标题；有意义时显示会议时间或目标关系。
2. 一句 **现在怎样**。必要时连带“当前未知”或“仍需你确认”。
3. 两个稳定入口：**当前 / 记录**。
4. 当前页主区域：此时最值得看的内容。
5. 次级“背景与来源”：简短背景、来源入口、更新时间，详细回执按需展开。

“当前”不是 AI 自动重排的无限仪表盘；由确定性的工作状态选择有限的产品组件。页面主区域变了，标题、当前／记录入口、来源位置不变。

### 什么占据主区域

| 场景 | 主内容 | 最重要动作 | 不做什么 |
| --- | --- | --- | --- |
| 会议收到改期建议 | 原时间与建议时间、原因、影响范围 | 仅更新 Chrona 安排／忽略建议 | 不自动 RSVP、改外部日历或通知参与者 |
| Agent 交付报告 | 真正报告正文；必要附件在正文后 | 接受此版本／写修改意见 | 不让一排状态卡把文档挤到下方 |
| 等待外部消息 | 最后已知事实、缺少的信息、上次报告时间 | 获取继续跟进所需的上下文 | 不显示远程运行进度、重试／暂停外部 Agent |
| 托管任务需要输入 | 问题、必要输入、恢复后的范围 | 提交输入并继续 | 不把输入表单当权限批准 |
| 托管任务等待授权 | 具体权限、作用范围、可能副作用 | 明确批准／拒绝 | 不把授权包在含糊的“继续”里 |
| 有真实失败 | 失败点、已完成部分、可安全恢复路径 | 由现有运行契约提供的恢复操作 | 不把重新开始当无害默认操作 |
| 已结束 | 最终成果、结束时间、未清理的注意事项 | 查看成果／明确新建后续工作 | 不把 Cancelled、Completed、Done 混为一种 |

### 同时出现多件事

优先选择当前阻塞的用户决定，其次新交付，再次最近进展。不是硬编码“有结果就显示报告”。

所有待处理问题都保留可见入口。涉及权限、安全或不确定副作用的内容不因优先级折叠掉。正在阅读或填写时，新内容仅出现更新提示；不替换用户正在审阅的版本、不夺取焦点、不清空草稿。

## 6. 四条完整使用路径

### A. 会议改变时间

总览看到「收到改期建议」→ 打开会议 → 比较原安排与建议安排 → 看到“仅修改 Chrona，不修改外部日历”→ 确认。

确认后页面应变成：
- 当前 Chrona 时间已经更新；
- **外部邀请仍需处理**，而不是笼统“改期成功”；
- 记录保留原建议、用户决定及更新回执；
- 如果邮件发送结果未知，显示“先核对是否已发送”，而不是再给一个“发送”按钮。

若外部日历拥有该时间块，显示只读边界和来源入口，不提供虚假的本地应用按钮。建议过期／并发更新时先读最新差异，不能自动套用旧决定。

### B. Agent 交付 → 人反馈 → 新版本 → 接受

总览发现第二版 → 直接读报告 → 明确“当前第二版；第一版已接受”→ 写意见 → 保存。

保存后的消息：**“修改意见已记录，尚未通知外部 Agent。”**

提供“继续工作信息”：工作定位、精确版本、反馈、应保留的边界。用户复制给原 Agent 或另一个 Agent。复制不是发送，也不是执行权限。

Agent 重新读取真实反馈和版本后提交第三版 → 用户显式切换新版本并审阅 → 接受第三版。

- 第二版或第三版都不可覆盖第一版内容。
- 新版到来不自动改变原接受指针。
- 接受不自动完成工作，不自动加入 Goal 正式材料。
- 原型的“模拟新版本到达”位于**原型场景工具**，不是产品里的“让 Agent 工作”按钮。
- 通用复制交接能力目前属于提议，不是已上线发送／唤醒功能。

### C. 等待外部进展

用户两天后打开总览 → 看见「最后获知：资料收集中」和「当前进展未知」→ 打开看到缺报价与最后报告 → 复制跟进信息给日常 Agent。

重新接手者知道去哪里核查、哪些结果未知、不应重复哪些操作。没有收到消息不等于任务失败，也不等于 Agent 正在后台继续。

### D. Chrona 托管任务停住

总览可见「需要输入」→ 打开直接回答当前节点的问题 → 查看恢复范围 → 提交输入。

真正权限审批显示不同文案和决定，运行中保留暂停／停止等现有控制及其准确语义。仅在真实执行存在时显示执行详情，不让无 Run 的会议看到空执行图。

## 7. 创建与日常进入

- “记录工作”默认仅保存非自动工作，不用 Provider、不生成 Plan、不启动执行。
- 最少字段：标题；背景可选。时间、截止日期、关联目标按需添加，彼此含义独立。
- 在既有工作上添加来源／报告／成果，不因换 Agent 再建一件工作。
- 从邮件或日历登记时先按稳定来源身份查重；展示“已关联到这件工作”，不能凭标题去重或覆盖不相容的来源。
- 托管执行是显式选择的能力，后续独立配置成本、工具范围、审批策略；不能把“记录工作”做成隐形启动按钮。
- 新用户空页面提供“记录一件工作”和简短场景说明，不把示例工作悄悄写入真实账户。
- 没有目标、时间、Plan、Run、成果都是合法工作形态，不能满屏空卡片。

## 8. 信息分层：藏杂音，不藏风险

### 第一层：默认可见

事情名称、当前有用的事实、必要来源／新鲜度、关键问题、可用的下一步、执行副作用、未确定的外部结果。

### 第二层：点击后展开

各状态维度、参与者、详细来源、版本历史、操作回执、执行图、已处理问题。

### 第三层：诊断与技术细节

记录 ID、revision、命令回执引用、技术错误信息。用户正常处理工作不必阅读这些字段，排错时仍可定位。

不在层级中展示 secrets、原始 Provider 请求、完整 Run context。不能通过把“Agent 声称批准了”放进第二层，就把它转换成真实授权。

### 文案与操作名

| 不推荐 | 推荐 |
| --- | --- |
| 手动工作「可执行」 | 「已记录」或具体近况；不虚构正在执行 |
| 「确认并应用」 | 「仅更新 Chrona 安排」 |
| 「已发送反馈」 | 「意见已记录；未通知 Agent」 |
| 「成功」 | 说明什么已经成功、哪些动作尚未发生 |
| 「进展与回执」 | 一级用「记录」；回执作为记录详情 |
| 「接受」 | 「接受第 2 版」并显示其影响范围 |
| 「完成」 | 只用于对应领域的真实完成操作，不代替接受、参加、发送 |

术语简化仅用于界面，不要求大范围重命名协议或领域代码。

## 9. 日程与目标的边界

### 日程

保留时间轴能力。已安排时间与待确认提议有明显区别，提议不占据已确认时间。点击回到同一工作。截止时间与工作时间块分别表达；都不承诺通知送达。原型只验证局部日程汇总，不替代当前完整日历交互设计。

### 目标

目标回答方向、当前重点、成功标准与可复用正式材料。工作是推进目标的活动，正式材料是已经整理确认的积累。

保留既有 Goal Workbench 的资产语义：稳定资产、版本、草稿、收件箱、人确认。不能将 TaskResult 接受指针当成 GoalAsset 正式版本；外部成果接续／晋升尚需独立设计授权和工程阶段。

原型展示目标概览与已有虚构正式材料，但明确不提供外部成果一键晋升。没有目标的工作不因此低一等。

## 10. 视觉与交互语言

- **安静但不模糊**：暖白背景、深墨文字、青绿色主动作；琥珀只表示待确认／不确定，红色只用于风险和失败。
- 主要分组依赖留白、字号、行分隔，不给每个字段套卡片。文档阅读区有足够宽度和行距。
- 列表行给明确文字入口；行内按钮与整行点击不能产生嵌套交互冲突。
- 不能只靠颜色表达状态；来源归属和时间使用可读文字。
- 桌面：窄导航＋主工作区；背景侧栏不抢主内容。
- 平板：收紧导航，保持正文宽度；过长的背景信息移到下方。
- 手机：四个导航入口保持可达，正文单列；比较时间上下排列；按钮可换行，操作前影响说明不可隐藏。
- 键盘：可见焦点、跳过导航、原生对话框焦点约束、Esc关闭、关闭后回到触发点；前进／后退维持位置和草稿是生产验收要求。
- 支持系统减少动画偏好。首轮不依赖动效传递状态。
- 生产实现继续使用现有 shadcn primitives、i18n 与 pure model helpers；离线 HTML 原型不是新 UI 基础库，不可直接拷入生产替换这些规范。

## 11. 非理想状态同样是设计内容

| 情况 | 必须可见的内容／恢复路径 |
| --- | --- |
| 首次空工作区 | 为何可以记录工作；记录不会自动执行 |
| 筛选无结果 | 保留筛选与清除方式，不冒充全局无工作 |
| 正在读取 | 保持骨架，不用旧状态冒充最新状态；读失败后不静默清空 |
| 部分读取失败 | 成功读到的内容仍可用；具体失败区域单独重试 |
| 无写权限 | 内容可读、动作不可用并说明权限；不教用户绕过凭据 |
| 保存失败／结果未知 | 保留表单；核查原 requestId 结果，避免重复副作用 |
| 并发版本改变 | 原阅读版本与最新版本区分；要求用户切换／重新确认 |
| 建议过期 | 显示为何不能应用和最新差异；不自动修改 expectedRevision |
| 必需文件失效 | 报告仍可读；接受按钮说明阻断文件；不能降级成“已接受” |
| 已取消／已结束 | 无错误的“继续执行”；已有材料与历史仍可访问 |

原型实现部分状态用于体验验证；未实现的真实网络错误、服务端权限和文件安全必须在工程阶段验证，不能由 mock 测试冒充。

## 12. 能力清单：哪些今天就能承接，哪些只是提议

| 设计行为 | 当前基础 | 本提案的改变 |
| --- | --- | --- |
| 统一工作导航与具体近况 | Task、WorkRecord、托管状态存在 | 新视图投影；不自动转换所有 Task 为 WorkRecord |

## 13. 分阶段落地，而不是一次重写

### 0 — 现在：检验设计

离线原型＋用户任务测试。所有数据虚构、不接 API、刷新重置。先验证能不能看懂，再讨论细节颜色或组件实现。本文件不启动实施。

### 1 — 降低已有页面的理解成本

在用户批准后：精简导航；将 WorkRecord 当前页变成事项内容优先；成果正文优先；准确的作用范围／来源文案。保持旧 URL 和执行入口，不改数据模型、权限、运行语义。补 i18n、状态表测试及三尺寸 E2E。

### 2 — 统一总览和跨工作续接

在已有边界内定义只读工作投影（任务＋进展＋结果＋真实待处理），验证分页、排序、权限差异和部分失败。新增受限的复制交接信息，明确草稿与版本行为。不让前端 N 次请求全表来拼首页；若需要后端聚合 API，单独列入工程计划和测试。

### 3 — 后续能力另行立项

外部结果进入 Goal 正式材料、旧 Run／独立成果语义收敛等，沿 canonical phase gates。不能因为导航合并就偷偷做数据库迁移或扩展凭据。

每阶段独立验收；开发、部署、真实邮件／日历操作分别授权。保留前一阶段入口直到关键流程回归通过。

### 不改代码的替代方案

可以继续由日常 Agent 查读并口头概括工作，用户只在 Web 做必要决定。短期可用，也适合低频使用；但不能解决用户独自打开工作台时看不懂的问题。因此建议修产品结构，而不是只写一份操作教程。

## 14. 验收：用户不需要我在旁边讲解

让用户先自由操作，不解释模块含义，观察再询问：

1. 打开总览，能否在约 15 秒内说出“最近什么变了、哪件在等、哪件需要输入”？
2. 能否找到第二版报告正文，而不先研究状态卡？
3. 能否准确预测“仅更新 Chrona 安排”不会改外部邀请？
4. 能否保存反馈后知道 Agent 尚未收到，并找到下一次继续所需的信息？
5. 第三版出现时，能否说出第一版仍是已接受版，直到明确接受第三版？
6. 能否区分外部两天没消息与托管执行真实暂停？
7. 手机同样能完成比较、反馈、返回；无水平滚动和被遮挡的动作。

目标是理解与安全预测全部正确，不是强迫用户达到秒表 KPI。记录第一次误解和找不到的地方；若需口头解释才能继续，优先调整结构，而不是追加提示卡。自动交互测试与视觉检查仅作辅助，不冒充用户验收。

## 15. 本轮仍需用户判断的设计假设

- “总览／工作／日程／目标”是否比当前入口自然？
- 工作页的“当前／记录”是否足够稳定，还是经常需要直接访问固定的“成果”入口？当工作有多份长期使用的成果时，可能需要第三个入口，不能仅凭这批小样本决定永远两栏。
- 近况以分组列表为默认，是否足以掌握整体，还是用户更需要按目标分组？
- 接受成果后是否常常还要继续工作？先保持二者独立，暂不加一键“接受并结束”。

建议先使用原型，不先批准整套实现。用户认可的部分再转成可验证的工程计划。

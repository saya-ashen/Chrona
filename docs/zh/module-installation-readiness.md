## 安装检查

依赖安装完成后，依次检查 manifest/工具契约、入口类型、作者声明的离线测试、已有数据副本（必要时迁移）上的作者测试、进程启动、SDK 连接和独立协议 `ping` 回复，并保留受影响调用方的类型检查。全部通过才启用。任一失败仍拒绝该版本，旧版本与真实数据保留。

安装不编造工具参数、caller、定时事件或业务效果。`ping` 由 SDK 直接回复，不触发模块事件处理器；错误协议、退出或超时仍使安装失败。不再使用这些调用推断幂等键是否正确。作者测试负责真实输入与键的业务用例，内核原有调用身份、权限、预算、幂等和停止证据约束保持执行。数据副本测试输出只保留退出结果，避免把真实内容写进公开构建报告；初始空数据作者测试保留既有输出。

## 就绪报告与诊断

模块使用 `chrona.reportHealth()`（路由目标 `modules.report-health`）报告：

- `ready`：模块认为当前已就绪。
- `needs_configuration`：需要配置，附原因和下一步。
- `degraded`：部分能力可用。
- `unknown`：模块无法确认。

`summary`、可选 `nextAction` 上限各 300 字符；不能包含凭据或私人内容。`validForSeconds` 默认 300，允许 1–3600。报告由当前连接的模块身份提交，只能影响自己的就绪信息，不授予权限、不改运行状态、不消除业务故障。报告参数与响应不写入 invocation。报告保存在当前进程实例的内存中，重启后重新上报。

Chrona 继续独立观察进程与通信。没有报告、报告过期或进程不可用时，就绪状态为 `unknown`；保留报告来源、时间与过期标记，避免把进程运行中误认为业务可用。

声明 `healthCheck: true` 的模块处理 `on("health", ...)`。常驻进程启动后、应用设置变更后、用户保存/删除凭据后（通知声明该凭据的应用），以及用户在应用概览点击“重新自检”时触发独立诊断事件。该事件不复用 `activated`，不会隐式重做页面登记或业务任务。非声明模块仍可自报；没有健康处理器的模块不因手动刷新被执行业务工具。配置通过环境或外部系统改变时，可手动刷新；报告也会按有效期转为未知。

诊断处理器应只读检查配置与依赖，不能发送消息、修改项目或产生付费请求；需要这些效果的验证由独立明确授权的业务入口执行。trusted-local 仍具备本地 OS 权限，声明和诊断约定不构成恶意代码隔离。自检处理器拒绝时显示未知，保留诊断错误，不因为配置问题关闭业务进程；通信超时或进程退出仍走原运行时故障机制。自检成功不清除业务失败计数、不验证业务恢复。

`coding` 的自检只读取已授权编码位置。没有位置报告待配置；位置离线报告部分可用；不检查真实模型调用、不启动执行。具体项目基线、预算、caller 与执行权限仍在每次实际工作入口检查。其他尚未实现自检的模块显示未报告，不推定已就绪。

# Chrona 平台 v2：总体架构

状态：v2-1、v2-2（含内置模块机制与 `files`）、v2-3（内置 `remind`、模块 `model` 能力）、v2-4（owner API、`listen`、救援控制台、`chrona admin`、内置 `mcp`、`qq`、简化 `web`）、v2-6（模块依赖）已在 `platform-v2` 分支实现（2026-10-23），其余分篇为草案。本文是 v2 的总纲，细节见 §10 列出的分篇规格。
用户 2026-10-22 决定：**删除"事务"概念**，以本文的模块（应用）与会话重新设计。[steward-goals](steward-goals.md) 已按本文改写；原 `steward-workspace.md`（事务工作区模型）已删除。
P0–P5 的实现记录见 [platform-upgrade-plan](platform-upgrade-plan.md)。

## 1. 定位

Chrona 是一个**随用户需求变化的工具**。它可以是日历、文件编辑器、信息推送、自动化助手……这些不是预设的功能，而是装在 Chrona 上的模块。**Chrona 的形态 = 当前启用的模块集合**；需求变了，Provider 提出新模块或修改已有模块，Chrona 随之改变。

## 2. 四个概念

| 概念 | 是什么 | 会不会生长 |
|---|---|---|
| **内核** | 权限、预算、调度、模块生命周期、模型网关、用户接口、救援 | 不会，AI 不能改 |
| **模块（应用）** | Chrona 的全部功能：日历、文件、提醒、网页、QQ、邮箱…… | 会 |
| **Provider** | 理解需求、需要判断的工作、提出或修改模块（现在是 Pi） | 不会（它的循环不生长） |
| **会话** | 与 Provider 的一段对话上下文；划分方式由入口模块决定 | 随对话产生 |

已删除：事务（`Affair`）、事务目录与内核 git、P3 并行模拟与"纯度"约束、内核里的提醒 / 网页 / QQ / MCP / 连接器代码。

```
          你（网页 / QQ / MCP / 救援控制台 / 命令行）
                            │
┌──────────────── 内核（不可变）─────────────────┐
│ 策略与审批 · 预算 · 调度与事件 · 模块网关与监管 │
│ 模型网关 · owner API · 认证与凭据 · 会话 · 救援 │
└───────┬──────────────────────────────┬────────┘
        ▼                              ▼
  Provider（在会话里工作）          模块 = 应用
  content/ 下看到各应用内容          files · calendar · remind · email ·
                                    web · qq · mcp · 生长出的模块……
```

## 3. 内核

| 部分 | 职责 |
|---|---|
| 策略与审批 | 确定性规则：auto · notify_after · preapproved · ask · never；外部文本不能授权 |
| 预算 | 通知（即时 / 汇总 / 仅网页、安静时段、日上限）；运行（全局与按会话）；模块（模型调用、唤起 Provider、通知） |
| 调度与事件 | 定时、入站条目、工具调用、HTTP、内容编辑，投递给模块进程 |
| 模块网关与监管 | 提交 → 构建 → 审批 → 启用 → 回滚；启动、停止、重启模块进程 |
| 模型网关 | 模块的模型调用；用户指定确切模型与上限，不自动回退 |
| owner API、认证、凭据 | 入口模块只经 owner API 工作；凭据只交给声明它的模块 |
| 会话 | 按键管理对话上下文、Provider 会话、临时工作目录、检索 |
| 救援控制台、命令行 | 最后的入口（[v2-4](platform-v2-4-entries-rescue.md)） |

## 4. 模块 = 应用

| 组成 | 说明 |
|---|---|
| 代码 | 常驻、事件驱动的进程（[v2-1](platform-v2-1-runtime.md)） |
| 私有数据 | 只有模块自己读写 |
| 内容区 | 用户与 Provider 可见、可改的文件（Markdown、面板、`*.ui.json`、配置）；网页渲染为该应用的页面；被修改时模块收到 `content_edit` 事件（[v2-2](platform-v2-2-sessions-content.md)） |
| 工具 | 给 Provider、owner MCP、其他模块 |
| 能力声明 | `notify_user`、`wake_provider`、`network`、`model`、`secret:*`、`host:*`、`owner`、`source`、`calls`、对外动作 |

模块彼此独立，不归属任何容器；能力声明就是它的全部权限。

内置模块（随 Chrona 发布，初始版本免审批，之后可改、可替换、可回滚）：

| 模块 | 作用 | 规格 |
|---|---|---|
| `files` | 用户文档：内容区就是文件本身；网页编辑、MCP 工具；Provider 的产出默认放这里 | v2-2 |
| `remind` | 到点提醒 | v2-3 |
| `web` · `qq` · `mcp` | 交互入口 | v2-4 |
| `email` · `chino-health` | 事件源 | v2-5 |

## 5. 会话

借鉴 Hermes Agent：会话就是与 Provider 的对话上下文，不带权限含义；怎样划分由入口模块决定（v2-2 §2）。

- QQ 固定一个会话，`/new` 开始新会话；网页有会话列表，可切换、恢复；救援控制台固定一个。
- 闲置或每天定时自动重置，重置前 Provider 保存需要长期记住的内容；`chrona_session_search` 检索历史会话。
- `wake` 与模块 `wakeProvider` 在全新会话中运行，指令自带上下文；结果投递回创建它的会话或以通知送达。
- 长期状态不在会话里，而在应用（内容区、`files`）与长期偏好里。

## 6. 一个需求怎么走

用户说一句话，Provider 在当前会话判断：

1. 直接回答。
2. 一次性工作（调研、写材料）：在会话里做，产出写进某个应用的内容区，通常是 `files`。
3. 过段时间再看：设 `wake`，到点在新会话中按指令继续，结果回到当前会话。
4. 现有应用能办：调用它的工具（例如 `calendar.add_event`）。
5. 办不了或会反复出现：提出新模块或修改已有模块 → 构建 → 审批 → 启用。**这一步就是 Chrona 随需求变化。**

## 7. 权限与预算

- **模块**：启用时批准的能力就是全部权限；新增能力必须重新审批。"更新自动启用"按模块授权（无新增能力、无迁移、测试与试启动通过；告知带 diff 链接）。
- **Provider**：每次工具调用由策略层判定；运行次数按全局与会话计。
- **入口模块与 L1 变更**：只能在救援控制台批准（v2-4）。

## 8. 信任链与恢复

救援控制台（不可变、独立端口与凭据，只有对话与审批）→ 批准入口模块 → 入口模块代表用户 → 用户批准其他一切。

| 情况 | 办法 |
|---|---|
| 普通模块坏了 | 连续失败自动暂停并通知；在任一入口让 Provider 回滚 |
| 网页 / QQ / MCP 坏了 | 救援控制台对话回滚，在控制台批准 |
| Provider 也坏了 | 主机上 `chrona admin` 回滚后重启 |

## 9. 不变式

1. 运行中的模块代码一定是某个已批准、按 hash 存储的版本。
2. 模块只能调用清单声明且 L1 允许的内核方法；凭据、本机路径只给声明者。
3. AI 不能修改内核、L1、救援控制台与命令行；对平台的唯一写入方式是提案。
4. 通知全部经预算；已执行的对外动作不因重启重复执行。
5. 回滚不悄悄丢数据：数据格式不兼容时由用户选择。
6. 救援控制台与命令行在任何模块损坏时仍可用。

## 11. 未决问题

- 模块进程并发上限与空闲时长。
- 模型网关经 Pi 调用的确切形式。
- 网页模块的离线构建与依赖审查。
- Windows 上的隔离方案（模块已可未隔离运行）。
- 按主机放行网络（P5 HTTP 代理）与 `network` 模块外传凭据的风险。
- 生长出的模块不再使用后的清理（停用、删除数据）的交互。

# 编码工作台参考项目调研

> 当前状态：Coding 与 coding-web 已退役，包含旧 work-v2；当前 Chat 独立拥有会话与执行记录。本文的 Coding/Editor 接口、源码路径、验收和部署描述仅作历史记录，不是现行接入指引。详见[Coding 退役说明](coding-retirement.md)。

调研日期：2026-11-08。状态：公开资料调研与设计建议，尚未冻结界面，也未开始新版页面开发。顺序见[开发路线](development-roadmap.md)，旧 Coding 能力已退役，现状见[Coding 退役说明](coding-retirement.md)。

用户纠正了前一轮的参照假设：Orca 不一定适合 Chrona，而且其界面过于复杂。本轮撤回“Orca 风格”和固定三栏作为设计前提；先比较具体交互，再选择最小页面结构。本文不对外部 Orca 的当前实现作源码评审。

## 1. 调研方法与结论边界

使用项目官方仓库、官方文档和官方界面截图；核对重点是开始工作、找回工作、理解进度、介入与检查成果。没有安装运行这些外部项目，没有用同一任务完成对照实验，也没有测量加载速度或用户完成时间。因此“适合参考”“复杂度高低”是结合 Chrona 需求的判断，不是客观易用性排名。

资料是访问当日的在线页面与默认分支，未固定为发行版本。截图用于理解界面层级，不保证覆盖当日所有功能。不能根据一张简洁截图推断其完整产品或实现简单；不依据 stars、宣传语或支持模型数量选型。本文推荐借鉴交互，不建议引入另一套 Agent 运行时；代码复用、许可证和依赖成本尚未评审。

**建议重点参考 OpenCode、HAPI、T3 Code；Conductor、Vibe Kanban 作为工作与审查的专项参考。CloudCLI 用于比较完整 Web IDE 带来的范围扩张。Happy 和 OpenHands 作为补充对照。没有单一项目适合整体照搬。**

## 2. Chrona 的选择标准

> 🧠 **From Hindsight memory (Basic coding web workbench)** — 既有基础页的目标是创建或选择工作、查看进度/成果/问题、补充信息和停止工作，并复用共享页面渲染与 coding 自有接口；记忆不证明该页已经生产部署。本轮核对了 coding 的入口、会话日志、Agent 适配及 workbench 实现。

当前源码核对点：

- `packages/engine/src/modules/steward/external/coding/index.ts`：页面登记、业务操作与真实模块调用身份。
- `coding/sessions.ts`：业务会话与所选工作的持久记录；它不是 Pi 会话文件。
- `coding/agent.ts`：coding 对 Agent 原语的适配。
- `coding/workbench.ts`：基础页的有界列表、进度、问答、停止和成果操作。
- `AGENTS.md`、`PRODUCT.md`、`docs/zh/steward-goals.md`：应用拥有业务；成果不能只藏在聊天里；页面不应变成执行日志控制台。

据此，参考项目需要回答：

| 标准 | 要观察的问题 | 对 Chrona 的含义 |
| --- | --- | --- |
| 开始工作 | 开始前必须理解几个对象、做多少选择？ | 已授权项目与目标应能直接开始；执行器、预算等按需调整 |
| 离开与回来 | 能否快速找到原工作、看懂变化？ | 持久工作列表、明确的待答复/进行中/可检查状态；不只恢复聊天滚动位置 |
| 介入 | 补充要求、回答问题、停止是否自然？ | 原生问题控件和明确输入目标；请求停止与确认停止要区分 |
| 成果 | 回复、文件、差异、验收能否直接找到？ | 成果有独立入口和版本；“已接受”不等于提交或合并 |
| 多入口 | 同一工作是否能跨客户端接续？ | Web 是业务状态的操作入口，不拥有独立执行事实或私有队列 |
| 实现成本 | 是否必须同时建设终端、编辑器、浏览器、Git 工作流？ | 首版选择完整但窄的工作闭环；不能仅用“折叠起来”掩盖这些功能的实现成本 |

这里的“工作”是用户交代并可回来检查的业务事项。会话用于沟通，工作树用于编码隔离，Run 用于执行治理；不要求用户先学习这些内部层次。

## 3. 候选项目比较

下表的“借鉴”和“取舍”是本次判断，产品事实见第 8 节的一手来源。

| 项目 | 已核对的定位/能力 | 最值得借鉴 | 对 Chrona 的取舍 |
| --- | --- | --- | --- |
| **OpenCode** [S1] | 官方 Web 文档描述浏览器连接服务、项目/会话及会话接入；Web 页可与终端入口配合 | 以当前会话为中心，减少开始和继续工作的摩擦 | 作为主交互参照；不能让 coding 工作直接退化为运行时会话，也不能把 provider 会话文件当业务数据库 |
| **HAPI** [S2] | CLI、Hub、Web/PWA；支持会话接续、消息、权限交互和变更查看 | 稳定列表、未读/状态提示、手机上的查看与介入；尤其是列表不被后台输出不断重排 | 作为跨入口与恢复参照；它也有终端、文件和多种配置，不能据此称整个产品简单。Hub/同步实现不直接搬入 Chrona |
| **T3 Code** [S3] | 自称 agent harness control surface；有 Web/桌面/移动入口及项目、线程、外部 Agent 接入文档 | 独立操作界面如何组织项目与线程、让客户端连接执行侧；结合官方截图观察主区域与辅助区域 | 作为页面组织与边界参照；不引入其多执行器平台或把 Chrona 的所有应用包装成编码线程 |
| **Conductor** [S4] | 以 workspace 组织编码；官方文档区分 Chat、Diff、Terminal 与审查步骤 | 工作隔离、检查改动、审查上下文；把工作状态与可检查成果联系起来 | 用于成果流程参考；其分支/PR/合并流程不能直接映射 Chrona 的“接受成果”。不默认移植其完整 workspace 生命周期 |
| **Vibe Kanban** [S5] | 看板、任务/工作区、Agent 执行及内置差异审查；官方提供工作区截图 | 多项工作需要用户注意时的概览、逐文件审查与反馈入口 | 作为后续多工作及审查参照；是否需要看板由实际任务量决定，不先引入任务管理产品的全部对象与状态 |
| **CloudCLI / Claude Code UI** [S6] | Web/移动界面，项目与会话；还包括 shell、文件编辑、Git 和浏览器功能 | 响应式会话页面、项目切换与历史接续 | 用作范围对照：完整 Web IDE 会显著增加工程面。只选取会话交互，不将其功能清单变成 Chrona 首版要求 |
| **Happy** [S7] | 当前资料包括桌面与移动、多模型、会话同步及多人操作；原 CLI 也可将会话接到手机 | 不同设备继续同一会话的连续性 | 补充参考，避免依据旧资料把当前 Happy 只当成简单手机遥控器；不引入其中继、加密与多人系统作为本轮依赖 |
| **OpenHands Agent Canvas** [S8] | 当前仓库已是可自托管的 Agent 控制界面，连接独立 Agent Server；SDK、客户端与自动化分仓，支持第三方 Agent 和多个后端 | 界面与执行侧分离、嵌入宿主产品时的边界 | 作为架构和组件组织的补充参考；不照搬自动化服务与多后端管理。不能用早期 OpenHands IDE 印象评价当前 Canvas |

首轮实际查看了 OpenCode 的新建/活动会话截图、CloudCLI 的桌面与移动截图、Vibe Kanban 的工作区截图，并阅读其他候选的官方功能和流程资料。截图观察只能证明其展示方式，不能证明实际操作流畅或状态恢复可靠。

此外必须区分设计参考与持续服务依赖：Vibe Kanban 已在 2026-04-10 宣布公司关闭、项目转向开源社区维护；Conductor 的 0.93.0 公告表示逐步收尾，Cloud 将于 2026-11-13 转为只读、2026-11-20 关闭，本地版本维护到 2027 年初。它们仍有交互参考价值，本轮不将其托管服务或产品后续路线当作 Chrona 的依赖。[S4][S5]

## 4. 具体可借鉴的交互

### 4.1 HAPI：回来时先找到工作

官方 session-list 文档明确：默认列表按用户最后输入排序，后台输出不反复重排普通条目，同时更新未读/状态。它另有可选的进行中分组，会随状态迁移条目；因此稳定顺序不是对所有视图的绝对承诺。[S2]

对 Chrona 的建议：后台进度更新只改状态与未读提示，用户输入或主动排序才改变列表位置。正在阅读旧进度时保留位置，显示“有新进展”；用户位于末尾时再自动跟随。这个细节比增加一个面板更直接影响日常使用。

### 4.2 OpenCode：操作入口可以很轻

官方 Web 使用方式从连接服务、选择项目到创建/继续会话展开；终端可接入同一服务的会话。[S1]

对 Chrona 的建议：默认让用户选择已授权项目并输入目标；项目、执行位置、模型与预算配置不必全部变成开始前的必填表单。借鉴会话的操作自然度，但工作状态、成果和待答复事项仍要有明确入口；仅做聊天壳不能满足产品目标。

### 4.3 T3 Code：界面与执行侧有清楚边界

官方定位与内部概览将其作为对现有 Agent harness 的控制界面，并描述服务端、客户端和 provider adapter 等分工；外部 Agent 还能经其 MCP 操作。[S3]

对 Chrona 的建议：借鉴“多个入口围绕同一工作”的组织方式，不采纳其运行时架构作为本轮重构要求。coding 应继续提供页面所需的业务视图和动作；Web 展示业务状态，不能直接读 Pi 文件、控制进程或重新维护执行事实。

### 4.4 Conductor / Vibe Kanban：成果要能检查

Conductor 的官方流程把差异审查作为 workspace 工作的一部分；Vibe Kanban 提供内置文件差异和审查反馈。[S4][S5]

对 Chrona 的建议：完成后直接提供成果与差异入口，审查视图可以替换主内容区或单独展开，不要求常驻右栏。明确正在看哪个成果版本；阅读差异、接受成果、提交/合并、清理工作树分别处理。不能为了模仿外部流程，把业务验收按钮偷偷变成 Git 操作。

## 5. 对页面方向的建议：作为待验证假设

**默认只保持一个主工作区；工作列表可收起，成果按需查看。** 主区可以在沟通和成果之间切换；待答复问题出现在当前工作明显位置，进度细节可以展开。不是把所有能力放进一个长聊天流，也不是把文件树、终端、diff、工作图同时固定在屏幕上。

暂不选择固定三栏。建议 W0 用相同内容制作两种低保真方案，再选择：

| 方案 | 默认结构 | 可能适合 | 必须验证的代价 |
| --- | --- | --- | --- |
| A：会话主区 + 按需成果 | 可收起工作列表；主区显示沟通/问题；切换查看成果与差异 | 一次主要跟进一项工作，频繁补充和答复 | 成果不能因藏在切换项中而被忽视；审查时能方便回到相关要求 |
| B：工作收件箱 + 工作详情 | 列表优先显示待答复、可检查及最近工作；进入详情后操作 | 经常离开后回来，或同时有数项后台工作 | 不能为每次输入增加跳转，不能逐渐膨胀成任务管理系统 |

两者可以共享同一份业务数据，不需要引入第二种工作模型。桌面可显示列表与详情；窄屏进入单项详情，通过明确返回入口切换。只有同一任务反复需要并排看要求和差异时，才考虑可选分屏；不把拖拽、多面板布局持久化或窗口系统作为初版目标。

**建议默认可见的信息：** 工作目标与项目、当前状态和一句进展、待答复问题、补充输入或当前主要动作、成果入口。

**建议按需展示的信息：** 完整进度和工具参数、文件差异、旧成果版本、工作树信息、执行用量与技术详情。停止待确认或成果不完整等影响决定的信息不能藏进技术详情。

**建议暂不建设的能力：** 完整文件编辑器、交互终端、嵌入式浏览器、任意面板编排、多人协作、Agent 集群视图。这些是首版范围建议；有实际使用理由时再调整，不是永久排除。

## 6. 与 Chrona 架构的结合

1. **业务拥有页面。** coding 聚合工作、会话、问题和成果；web 负责通用呈现和交互。不为工作台增加内核业务页面。
2. **共享业务事实。** Web、owner MCP 和仓库外编辑器应通过同一 Coding 应用协议读取或修改工作（旧 Editor 服务应用已[退役移除](editor-retirement.md)）；并非把所有入口原始聊天历史强行合并。跨入口显示谁补充了什么、当前动作作用于哪项工作。
3. **执行控制沿用治理。** 页面不直接连接 Pi。保留请求去重、真实 caller、预算、停止证据和未知状态占用；显示“已请求停止”不等于进程已停。
4. **先补具体缺口。** 当前页面每次读取前 100 条事件并轮询、问题需要按文字填写、只显示最新 patch 等，都值得在 W1 改善。先核对现有事件/快照和成果接口，不能靠界面假装历史完整。
5. **不提前泛化。** 通用委托、Run/Call 和产出协议继续后置。业务工作/会话标识保持独立，通过已有 coding → Agent 适配衔接。

外部项目的“多 Agent”“会话”“workspace”等名字不必一一映射成 Chrona 新实体；优先提取用户动作及其状态反馈。

## 7. 开发前的最小验证

W0 的下一步应是以下可审查材料，而非开始搭建完整界面框架：

1. 用相同的五个场景比较 A/B 两份低保真页面：开始工作；离开回来；回答问题；请求停止但未确认；检查并接受一份成果。
2. 同时覆盖一项正在执行、另一项等待答复的情况；从别的入口补充后，Web 能看见同一工作变化。
3. 标出每个动作对应的现有 coding 工具、缺失字段/能力和最小实现成本；以此决定 W1 范围，不凭竞品功能清单加项。
4. 在桌面、平板、手机尺寸检查主动作、内容阅读与返回路径。记录用户实际选择和阻塞，再冻结结构。

建议重点回答：能否一眼知道是否需要自己行动？是否需要找按钮、切换多个面板才能补充？看成果时是否知道版本和完整性？能否区分停止请求和确认？回来后是否需要重读整段聊天？这些结果比面板数量或功能总数更有决定性。

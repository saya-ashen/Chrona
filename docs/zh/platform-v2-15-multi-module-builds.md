# v2-15 规格：一次构建修改多个模块，一张审批一起启用

状态：已实现（2026-10-26）；第 6 节的三点已由用户确认，与草案的差异见第 7 节。依赖 [v2-13](platform-v2-13-modules-tools.md)、[v2-14](platform-v2-14-contributions-events.md)。

## 1. 背景

2026-10-25 的“Trending 简报用 Markdown 显示”需要同时改 `github-trending-daily`（声明格式）、`notify`（校验、保存并透传格式）、`qq`（按格式选择消息类型）。按 v2-13 只能一个模块一次构建：

- 构建会话不能改别的模块，也不能为别的模块发起构建，只能在回复里写“请勿单独启用”，再由用户回到主会话逐个发起（其间一次启动还失败了）。
- 三个候选各有一张审批卡，启用顺序全靠用户：先启用调用方，调用方传的新参数会被旧的被调方拒绝；先启用被调方则无害，但没有任何地方表达这个顺序。
- 每个构建只能用假内核测自己，跨模块的参数契约要等真实启用后才暴露。

## 2. 改动

### 2.1 一次构建声明多个模块

- `modules.build` 的 `name` 改为可选，新增 `modules: slug[]`（1–4 个，不重复）；两者必须二选一，`name: x` 等价于 `modules: [x]`。`goal`、`examples`、`files`、`intent` 描述的是整个改动。
- 构建会话的标题为“构建模块 a、b、c”；`current/<module>/` 分别保存每个已有模块入队时的启用版本快照；新模块没有快照。
- 构建提示要求：每个模块写在独立子目录；对已有模块先用无 hash 的 `modules.checkout` 比对最新启用版本；跨模块的新参数要在被调方的工具定义和测试里体现。
- 预算：仍占一个新建额度、一个队列位置；每轮提交上限按模块数放大（`maxSubmissions × 模块数`），单轮时限不变。
- 声明之外的模块不能在这次构建里提交（`propose` 以 `forbidden` 拒绝），防止构建者顺手改别的应用。

### 2.2 候选组

- 构建会话中，被声明模块的候选通过检查后进入 `pending_review`，但**不单独生成审批卡**，也不尝试自动启用。
- 每个声明的模块都有通过检查的候选后，Provider 调用新工具 `modules.request-group({ versions: [{ module, hash }] })`（仅构建会话可用）：
  - 必须恰好覆盖本次声明的全部模块，每个 hash 都是本会话提交、当前处于 `pending_review` 的版本；
  - 内核生成**一张** `activate_modules` 审批，`payload` 绑定全部 `(moduleId, hash)`；
  - 同一模块更早的待审候选和审批照 v2-13 规则过期并标为已取代；这些模块的单独审批卡同样过期。
- 只声明一个模块的构建保持现状：单独的 `activate_module` 审批，可以自动启用。

### 2.3 一起启用

- 批准 `activate_modules` 时，在**一个事务**里逐个检查并启用全部版本，只生成**一个**新的 generation；任何一个检查失败（版本状态变化、策略禁止、监听路径冲突、内置版本规则）则全部不启用，审批标为失败并说明原因。
- 第一版只支持**不需要数据迁移**的版本；任一版本需要迁移时，`request-group` 直接拒绝，并提示先单独构建、审批、迁移该模块。跨模块的迁移需要两阶段提交，不在本版做。
- 组审批不能自动启用，即使每个模块单独都满足自动启用条件。
- 回滚仍按模块进行：要撤回一组改动，就逐个回滚到组启用前的 hash（generation 里有记录）。审批详情列出这些 hash，方便回滚。

### 2.4 审批卡

- 网页：按模块分节，每节显示与单模块审批相同的内容（权限、意图、清单与代码差异、测试、hash），最上面列出“这组改动一起启用：a、b、c”。
- QQ 等聊天渠道：沿用精简规则，每个模块一行权限摘要和改动要点，结尾提示到网页查看完整差异。按钮仍然是“批准 / 拒绝”；不提供“始终允许”（组审批不进入自动启用）。

### 2.5 主会话

- 主会话 Provider 的提示补充一条：一个需求要同时改多个模块时，用一次 `modules.build({ modules: [...] })`，不要拆成多次构建再请用户按顺序启用。

## 3. 不变

单模块构建、提交快照与内容哈希、全部构建检查（沙箱测试、数据连续性、试启动、键检查）、构建队列与预算、停止/修改需求、内置版本规则、回滚。

## 4. 不在本版

- 构建期间在一个假内核里同时启动多个候选，做跨模块集成测试（第一版仍各自用假内核测试，依赖用桩）。
- 需要数据迁移的组启用（两阶段：先在副本上迁移所有模块，再一起切换）。
- 组内声明启用顺序或依赖；一起切换后不需要顺序。

## 5. 验证

- 表格测试：`modules.build` 的 `name`/`modules` 校验；声明外模块的 `propose` 被拒；`request-group` 缺模块、多模块、hash 不属于本会话、状态不是 `pending_review`、需要迁移时的拒绝。
- 组审批批准后：全部模块的 `activeHash` 在同一个 generation 里切换；其中一个检查失败时，全部保持原状、审批标为失败。
- 组审批的聊天通知：每个模块有权限摘要和改动要点，不含差异和 hash。
- 回归：单模块构建和审批的现有测试不变。

## 6. 用户确认（2026-10-26）

1. 一次最多 4 个模块。
2. 第一版不支持需要数据迁移的组启用：这类模块先单独构建、审批、迁移，其余再一起启用。
3. 组审批不进入自动启用，只能由用户批准一次。

## 7. 实现与草案的差异

- 没有新增审批动作：组审批仍是 `activate_module`，`moduleId` 为空，`payload` 为 `{ kind: "activate_modules", versions: [{ moduleId, hash }] }`。因此沿用现有的权限策略（不新增策略项）；QQ 与内置网页只在审批绑定单个模块时显示“始终允许”，内核也拒绝以 `always` 批准组审批。
- 审批状态没有“失败”：任何一个模块检查不通过时，整个事务回滚，全部模块保持原样，审批仍记为已批准但未生效，错误返回给批准的一方（与单模块启用失败的现有行为一致）。
- 构建声明的模块由内核在受理构建时记在 `build_request` 审计里（`modules`），不从构建目录读取；`propose` 在建版本之前拒绝声明之外的模块。这条限制也适用于单模块构建。
- 组成员通过检查后，其审查内容（清单与代码差异、意图、测试）存为 `module_review` 审计，由 `request-group` 合成一张审批。合成预览保留每个模块的必填部分，代码差异按模块平分剩余篇幅并注明截断；必填部分超过 20000 字时拒绝合成，提示拆小改动。
- 组内任一模块出现新的候选（无论来自哪个会话），整组审批随该模块的其他审批一起过期。
- `m_modules_request_group` 只出现在构建会话的工具目录里。

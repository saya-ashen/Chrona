# 内核公开 API 目标规范

状态：2026-11-10 用户授权改造；2026-11-11 先前六命名空间方案已完成记录中的离线检查，**完整门禁未通过、尚未冻结**。2026-11-11 用户进一步授权实现本文件第 9 节的 Provider 注册制与七工具 Agent 设计，**源码改造及定向离线验证已完成，尚无一次完整全绿的全量运行，未部署**。既有实现与证据见[API 实施记录](kernel-api-implementation.md)，先前阶段的检查不证明新增 Agent 合同已经通过验收。本次使用受控假进程验证，不调用真实模型或账号、不迁移现有数据。

产品目标以[设计目标](steward-goals.md)为最高依据；本文件规定公开合同。下表第三列记录相对改造前实现的变化，不能代替验证证据。旧边界合同及其验收记录描述先前阶段，不作为新版接口清单。

## 1. 设计边界

内核目标提供一个调用原语及七个命名空间：`modules / approvals / secrets / settings / activity / timers / agent`。原六个命名空间共 35 个工具，新增 `agent` 的 7 个工具后目标共 42 个。通用 Agent API 归内核，内核不包含具体 Provider；Pi 作为默认预装的 Provider 模块注册能力，可使用其他模块提供的 Provider，也允许没有 Provider 时启动内核。此目标替代“Agent 是唯一不可替换内置应用、Pi 是唯一内置 Provider”的旧设计；当前源码已按此合同实现并完成记录中的定向检查，已部署实例仍使用先前版本，离线检查与线上可用性须分别记录。

内核保留真实身份、路由、精确授权、硬预算、单 Run 队列、租约、取消、实际停止证据、敏感交付、受控生命周期与持久唤醒。通知、会话、记忆、文件业务、页面、应用设置、业务调度策略和多消费者分发由普通应用承担。预装不授予权力；本地执行仍是 trusted-local，不承诺隔离同一 OS 用户下的恶意代码。

下表中的“保留”指能力及主要合同保留；“修改”指现有能力需要调整公开合同；“新增”不表示已经实现。所有列表、身份和参数仍须遵守通用合同。

## 2. 通用调用合同

| 项目 | 目标 | 相对改造前实现 |
| --- | --- | --- |
| 调用原语 | `chrona.call(target, args, options)` | 保留原语，修改目标类型 |
| 内核目标 | `"modules.list"` 等固定名称 | 保留 |
| 应用目标 | `{moduleId, tool}`，用真实应用身份寻址 | 修改：不再用 `<name>.<tool>` 寻址 |
| 选项 | `mode / key / reply / timeoutMs / expectedTarget` | 保留并补齐语义；目标固定使用应用身份与合同哈希 |
| 幂等 | key 只放调用选项；绑定真实调用者、目标、操作及请求参数；同 key 不同参数返回 `conflict` | 修改：移除参数内的 `requestKey / commandKey`，处理器接收内核绑定的调用元数据；普通应用自有业务字段不由内核重写 |
| 调用查询 | `chrona.callStatus` 查询自己的调用；首次回复丢失时可按原目标和 key 找回 | 修改：补充按原请求身份查询，不要求先取得 `callId` |
| 参数与返回 | 结构化对象；所有工具声明完整输入、输出 schema；空结果也明确声明 | 修改：移除 JSON 文本参数及缺失输出合同 |
| 普通列表 | `{cursor?, limit?} → {items, nextCursor}`；有界、稳定排序，cursor 不授予权限 | 修改：统一分页；可靠消费与流式事件不强行套普通列表语义 |
| 错误码 | `invalid / forbidden / not_found / conflict / unavailable / cycle / failed / unknown` | 基本保留，统一映射；文案不参与控制判断 |
| 目标固定 | 获准工具绑定真实 `moduleId / contractHash`；单次 Agent Run 的工具目录也固定 | 修改：补齐运行准入；源码版本 hash 与合同哈希仍分开 |
| 超时与取消 | 超时不证明未执行，取消不证明停止；未知效果不自动重放，未知停止仍占容量 | 保留 |

应用名仍用于 Manifest、展示、搜索及新应用创建材料；已有应用的调用和控制使用 `moduleId`，同名重装不得接管旧请求。新目标尚无 ID 时由材料准入绑定其创建身份。SDK 的 `chrona.dependencies` 提供内核绑定的当前应用 ID，进程启动时可用，事件交付时刷新；应用实际调用仍携带 ID，可用 `expectedTarget` 固定合同。生成的 `ChronaCalls` 类型按声明名称索引，只是编译材料，不授予权限或恢复名称寻址。

错误可带有限的机器可读 `reason`：`capacity / budget_exceeded / cursor_expired / reauthorize / unsupported / unconfigured / too_large / timeout / module_paused`。它说明恢复条件，不增加错误码；应用不能靠文案识别游标过期或重新授权。

调用 key 长度为 1–200，内核原样转交处理器。相同 key 重取提交结果得到当次固定回执；后续状态变化应使用对应 `receipt / operation / get` 查询，不能把提交重放当成实时状态查询。

幂等必须跨重启保存；嵌套调用不能不加区分地复用父调用 key。调用者身份由内核绑定，参数不能自称 owner、其他应用或某次 Run。批准只作用于精确动作和对象，读取元数据不授予执行权。

凭据、对话正文、有限事实等私密读结果不复制到通用调用账本。`callStatus` 可显示原调用完成，但省略未留存的 `output`；同 key 同步重放在无法重建原结果时返回 `unknown`。只读工具可明确发起一次新的读取，未知写入不能据此自动重放。已确认的普通 JSON `null` 结果使用 `output: null`，与省略 `output` 区分。

`callStatus` 表示工具调用是否返回；`modules.operation` 表示生命周期动作是否实际完成。一次成功返回可能只拿到等待审批的业务回执，两者不能混为成功。瞬时 ID、时间戳等允许不同，但关联及行为保证必须满足合同。

## 3. modules：发现、材料与生命周期（12 个）

| API | 功能与主要输入 | 相对改造前实现 |
| --- | --- | --- |
| `list` | 分页返回应用身份、名称、当前版本与状态 | 修改：统一分页 |
| `describe` | 指定目标返回合同详情；未指定时分页搜索可达工具；保留身份、合同哈希和输出声明 | 合并 `tools + reference`，保留有界摘要与按需详情 |
| `health` | 按 `moduleId?`、分页及详情选项返回运行与故障证据；不主动调用业务探测 | 合并 `health + diagnostics` |
| `admit` | 绑定提交方精确身份、完整目标集合和活动版本基线 | 修改 `admit-candidates`：改名、key 移至选项 |
| `source` | 将准入范围内的精确版本材料交给实际获准提交方 | 保留能力，统一字段与返回 |
| `submit` | 冻结并提交完整材料，返回固定 `receiptId`；不隐式选择 latest | 修改：key 移至选项 |
| `receipt` | 按 `receiptId`，或准入与原提交 key 查询固定结果 | 修改 `candidate-check`：改名及选择器 |
| `enable` | 启用指定 `moduleId` | 修改：身份、幂等与操作返回 |
| `disable` | 停用应用，保留数据；停止请求与停止确认分开 | 修改：同上 |
| `rollback` | 选择指定应用的已批准版本；恢复数据另行确认 | 修改：同上 |
| `remove` | 经审批及依赖、停止、备份、数据损失守卫删除应用 | 修改：同上 |
| `operation` | 按操作 ID，或原目标与调用 key 查询生命周期固定结果 | 新增 |

生命周期操作使用声明完整 schema 的回执，概念形状为：

```ts
{
  operationId,
  moduleId,
  status: "pending_approval" | "running" | "done" | "failed" | "unknown",
  approvalId?,
  result?,
  error?
}
```

`result` 按操作声明类型，`error` 使用固定错误码；使用判别联合约束各状态允许的字段，不能任意混搭。`done` 表示对应动作的合同后置条件已成立：启停表示持久选择和调用准入已改变，回滚表示版本选择/必要数据恢复已完成，删除表示删除已完成。启停或版本切换不证明进程已退出、新进程已就绪或业务已完成；实际运行与退出证据由 `modules.health` 的 `running / stopping / unknown` 等状态报告，未知停止继续保留容量与数据安全守卫。删除批准不等于数据已删除。操作回执不随应用删除或同名重装消失。

候选提交保留材料专用回执，明确区分检查、等待审批、版本获准与当前选中，不能把曾获准当作目前活动。保留精确基线、完整集合、不部分激活、丢回复后查询和审批后重查。单应用可以经正常提交及明确审批迁移自身数据；多应用集合暂不支持迁移。不新增独立公开迁移工具；这不是旧架构用户数据迁移授权。

## 7. activity：观察与有限事实（8 个）

| API | 功能 | 相对改造前实现 |
| --- | --- | --- |
| `runtime` | 观察运行时、队列及故障状态 | 保留 |
| `runs` | 分页查询有权限读取的运行状态，不授予执行或 transcript 读取权 | 修改：分页与身份字段 |
| `records` | 分页读取有界、脱敏的活动事实 | 修改：统一分页 |
| `usage` | 查询模型与唤醒用量及相应预算周期 | 新增：整合现有用量并补唤醒统计 |
| `consumer` | owner 读取、选择或清空唯一事实消费者 | 保留：明确 `moduleId`；切换保留停止与 revision 守卫 |
| `facts` | 当前消费者读取有界未确认事实和消费 revision | 保留消费语义，允许有界批量选择 |
| `ack` | 以 `revision + ids` 确认已私有持久化的事实 | 保留 |
| `withdrawals` | 按事实键查询持久撤回状态，供恢复投递前对账 | 保留 |

先私有持久化，再 ack，再决定投递。确认表示应用接收，不表示送达用户；消费者切换不重放已确认事实，不转移原应用的私有通知和回执。普通列表分页不能变成跳过未确认事实的消费捷径。

**不增加内核 `subscribe` 或多消费者游标。** 未来需要多消费者时，由普通分发应用成为内核唯一消费者，持久保存后 ack，并为获准下游维护独立进度、过滤和积压。分发应用负责访问控制及撤回传播；Notify 等投递应用恢复前仍须完成撤回对账。切换前已被旧消费者接收的记录仍归旧消费者，不假设自动转移。

## 8. timers：持久唤醒（3 个）

| API | 功能 | 相对改造前实现 |
| --- | --- | --- |
| `set` | `{id, schedule, payload?}`；schedule 为一次性 `at` 或固定间隔 `every`；登记或替换自己的 timer，返回 revision 与 `nextAt` | 新增 |
| `cancel` | 取消自己的 timer；重复取消幂等 | 新增 |
| `list` | 分页查询自己的 timer、状态与 `nextAt` | 新增 |

第一版不含 cron、日历业务或通用事件总线。schedule 精确形状为 `{kind: "at", at: ISO时间字符串}` 或 `{kind: "every", milliseconds: 整数}`，两者严格互斥。`at` 必须在未来，`every` 为 1 秒至 365 天并满足当前最小唤醒间隔；默认最小间隔 60 秒。每应用保留至多 100 个 timer ID 槽位（包括终态），应用可用同 ID 替换；payload 上限 16 KiB。到点投递 `timer` 事件，包含稳定 `eventId / timerId / timerRevision / scheduledAt / firedAt / payload`；应用据此去重。timer ID 作用域为实际应用身份，不由参数指定其他应用。

内核负责持久化、最小间隔、唤醒硬预算及重启后错过多次合并一次。同版本暂停期间不投递，恢复后合并过期唤醒；timer 绑定注册时的活动代码 hash，hash 改变后标为 stale，须由应用重新 set。尚未检查到旧 timer 前若回到相同 hash，可继续原 timer；一旦标为 stale 则须重新 set。取消或替换不撤销已送出的事件，但旧处理器的迟到返回不能覆盖新 revision 或取消结果。运行中断且没有完成证据时标为 unknown、停止后续唤醒，须由应用核对效果后显式 set。取消不撤销已执行效果，未知效果不自动重放，不承诺业务恰好执行一次。唤醒成功不证明业务完成或通知送达。timer 不直接启动模型，模型工作仍走 Agent 准入及预算。

| API | 功能与概念输入 | 合并或替代关系 |
| --- | --- | --- |
| `register` | Provider 模块登记或更新自己的 Provider 标识、显示名称、协议版本、能力、配置与执行入口 | 新增；登记绑定内核识别的实际模块身份与批准版本 |
| `providers` | 按 ID 查询，或分页列出已注册 Provider 的身份、可用状态、能力、协议及配置入口 | 合并发现与健康状态；不返回凭据 |
| `run` | 选择 Provider 发起执行；可新建上下文或继续 `contextId`，传入输入、获准工具与 `providerOptions` | 合并原 `context + run`；单次补全能力也由此发起 |
| `read` | 按 `runId` 读取状态和有界事件页，支持 cursor、limit、等待新事件，以及原生事件视图 | 合并原 `get + stream`，等待为零时立即查询 |
| `write` | 向指定运行发送输入，使用判别联合区分 `message` 与绑定问题 ID 的 `answer` | 合并原 `write + respond`，保留分别校验 |

| `native` | 将指定 Run 的 Provider 原生请求透传给其已绑定的后端实例，返回关联的原生响应 | 新增后端能力入口；内核不解释 Pi 命令 |

上表字段为概念合同，完整 wire schema、大小上限和默认值须在冻结前确定。所有写调用的幂等 key 使用第 2 节调用选项，不在参数中恢复 `requestKey`。所有读取均检查实际调用者，不因持有 ID 或 cursor 而获权。

### 9.1 内核与 Provider 模块的职责

内核管理上下文的执行关联、唯一 Run 队列、事件与交互关联、真实 caller、工具精确准入、预算、租约、取消、持久状态和 Provider 选择绑定。Chat 等应用继续持有会话列表、标题、业务历史与工作流程；上下文标识不把这些业务归入内核。

Provider 模块拥有后端进程、原生协议、模型与 thinking 选项、配置读写和设置页面、资源加载、后端恢复及实际停止证据。内核既不导入 Pi，也不解释 Pi 配置目录、启动参数或扩展路径。持续执行与一次性模型调用均经过注册后端，不能另留宿主硬编码 Pi 的补全旁路。单次补全使用 `run` 选择 Provider 声明的能力，并经 `read` 获取结果；不再增加内核 `complete / completion` 工具，具体执行类型与预算映射待补 schema。

模型、thinking 和 Provider 特有选项由后端报告支持范围并验证，内核记录运行实际生效配置及来源，不内置 `fast / balanced / deep` 分类。配置入口通过登记的模块工具或应用设置页面提供，不扩充内核 `configure` 工具。Provider 私有配置中的凭据不进入发现结果、普通事件、模型上下文或调用账本。

### 9.2 登记、生命周期与运行绑定

登记必须包含可调用的执行与配置入口，而非只有名称和静态选项。入口使用真实 `moduleId / tool / contractHash` 绑定；提供者身份和批准版本由内核从实际调用者取得，不接受参数自授身份。模块只可更新自己的登记，同名重装或其他模块不得接管旧登记。登记不授予 owner 权限，也不扩大调用方已有权限。

Provider 模块激活后登记，停用、移除或失联后不再接收新运行；可用性与登记元数据分别表达。生命周期失效取代独立 `unregister` 工具；事件回传复用绑定运行的认证通道，不增加任意修改 Run 状态的公开工具。

每次 Run 固定 Provider 登记身份、模块版本、协议、配置快照或可追溯 revision、工具准入和后端执行标识。修改默认 Provider 或配置不改变已有 Run；继续上下文必须验证后端归属与恢复能力，不能静默切换后端。后端失联或结果未知不得自动重跑任务；未知停止继续占容量，实际停止须有后端/宿主证据。更新、停用与移除仍遵守依赖及实际停止守卫。

### 9.3 Pi 使用用户配置

默认预装 Pi 模块不等于内核依赖 Pi；用户移除后不自动补装。Pi 默认使用用户明确选择的配置目录，继承其模型、thinking、Skill、扩展、Prompt Template 和上下文加载行为；专用配置目录是用户可选项。服务账户与交互用户可能不同，因此目录选择须明确，不能把服务账户默认目录冒充用户选择。

Chrona 接入工具桥、会话关联和运行控制，明确显示必要覆盖项、来源、生效范围和本次实际资源。不得继续让 Web 会话固定走 `minimal` 而跳过用户资源，也不默认用 `--no-skills / --no-extensions / --no-context-files` 等参数重新裁剪完整环境。原生工具与原生审批交互随所选环境工作；Chrona 桥接工具仍受实际应用的精确授权约束，额外资源不自动获得其他应用的权限。

这属于配置与能力加载选择，不构成 OS 沙箱。trusted-local 仍按服务用户的系统权限执行，不能以环境变量过滤、工具目录或 Manifest 宣称文件与网络隔离。

### 9.4 原生能力与 raw 输出

启动前的后端特有选项和命令行参数放入 `run.providerOptions`，由 Provider 校验与解释。运行中的原生命令使用 `native`，概念请求为 `{runId, request: {type: "get_state"}}`，幂等 key 放在调用选项。原生协议和版本由 Provider 描述，内核不维护 Pi 命令白名单；不支持的能力返回明确的 `unsupported` reason。

`native` 复用 Run 已绑定的同一后端实例、凭证作用域与请求关联，不另启动独立后端冒充同一会话。调用者仍须有权控制该 Run；原生透传不允许改写内核绑定的 caller、回调身份、工具准入或预算。启动生成、切换会话、中止等改变执行状态的原生请求必须由 Provider 与内核状态同步；若产生新的执行，应关联受治理 Run，不能形成第二套隐藏队列。具体状态同步合同须在实现前明确。

原生响应保留后端结构，原生事件通过 `read` 的原生视图按游标读取，不强制压成文本摘要。大输出通过事件分页或 Provider 所有的有界内容引用读取；缺失、游标过期和截断须明确，不能把截断 JSON 当作完整结果。raw 表示保留协议内容，不意味着关闭凭据脱敏或将全部原始内容写入通用日志。响应丢失、超时或结果未知时查询原调用与原执行，不自动重发可能有副作用的原生命令。

### 9.5 旧接口的替代关系

不再单独提供 `context / get / stream / respond / interrupt / complete / completion / configure / health / unregister / resume / wait / transcript`。上下文创建与继续归 `run`，状态与历史事件归 `read`，问题回答归 `write`，配置归 Provider 模块，健康状态归 `providers`；后端特有 transcript 和恢复操作由 Provider 支持并通过已登记入口或 `native` 使用。该收敛是目标替换，不授权恢复旧接口兼容层。

## 10. Manifest 与 SDK

| 项目 | 目标 | 相对改造前实现 |
| --- | --- | --- |
| `uses` | 纯依赖声明，`*` 不授予 owner 权限 | 修改 |
| `authority?: "owner"` | 明确申请代表用户调用 owner 工具；新增权力须绑定精确版本批准 | 新增，替代通配符提权；声明不等于获权，后续更新不得隐式扩大权力 |
| HTTP 入口 | `listen` 与 owner 权限独立，不隐式互授 | 修改相关判定 |
| `tools[].output` | 所有工具必须声明输出 schema | 修改：去除可选输出合同 |
| 其他 Manifest | 保留 `name / description / entry / tests / packages / secrets / model / effects / keepAlive / activated / listen / content / data / params` | 保留能力，不为改名将 `effects` 换成 `network` |
| SDK 事件 | `tool / call_result / activated / timer` | 新增公开 `timer`，不恢复旧 schedule 合同 |
| SDK 方法 | `call / callStatus / serve / exec / paths / secret / token` | 保留能力，更新调用与身份类型 |
| `emit` | 不作为绑定可选 Events 应用的内核 SDK 便捷接口；通过普通应用调用使用 Events | 如有导出则移除；各语言 SDK 尚待逐项盘点 |

原 Agent 应用接口按第 9 节迁往内核通用接口与 Provider 模块。项目、工作区、工作结果和业务编排继续归相应应用，不增加内核 `work-*` 业务接口组；底层执行及位置能力的精确合同须另行验证，不以旧同名重载作为冻结依据。

## 11. 可替换内核的长期目标

其他人或其他语言可以实现内核；应用依赖公开语义、SDK/wire 协议及 Manifest 合同，而不依赖当前内部模块、数据库结构或实现语言。**这是设计目标，不要求本阶段实现第二套内核、跨语言 SDK 或状态迁移工具。**

“相同输入返回相同内容”不足以证明可替换。替代实现还须遵守权限、生命周期、并发与幂等、丢回复、重启恢复、未知结果、事件投递、进程接入、敏感交付和哈希规则。非确定性时间戳、生成 ID 可不同，但格式、关联和行为保证一致。合同哈希须有语言无关的确定规范与测试向量，不依赖某语言对象枚举的偶然行为。

| 替换层级 | 条件 | 当前承诺 |
| --- | --- | --- |
| 新环境兼容运行同一批应用 | 满足公开 API、Manifest、SDK/wire 与事件语义，通过同一套独立黑盒合同测试 | 设计目标，尚未完成跨实现验收 |
| 接管既有实例 | 另须导入并验证应用身份、版本、私有数据、审批、回执、timer 及未完成操作的归属和恢复 | 长期目标；API 一致不自动构成状态兼容或迁移授权 |

未来用不依赖当前内核内部代码的合同测试验证不同实现，覆盖重复/并发提交、丢回复查询、审批期间重启、停止未知、timer 恢复、事实确认与撤回、凭据不泄露。仅静态 schema 一致或单次正常请求输出一致，不能宣称无缝替换。

## 12. 冻结前剩余设计工作

本文件确定能力归属与 API 目标清单，不将未决字段包装成已冻结协议。冻结前须补齐：

- 每个工具的完整输入、输出、权限、默认值、大小上限与状态判别联合；`describe / health` 的摘要和详情边界。
- key 作用域、跨版本查询、结果保留、操作恢复，以及调用回执与生命周期回执的关联。
- 新应用身份分配、依赖声明与 ID 绑定、合同固定及合同变更的明确拒绝行为。
- owner 权限申请、授予及版本更新规则，保留实际 caller 与审批后重查。
- timer 时间格式、预算耗尽、暂停/升级/取消、错过合并与未知投递的精确语义及恢复用例。
- Agent 七工具的完整 schema、Provider 登记冲突及生命周期、配置快照与上下文恢复、原生协议状态同步及事件保留；持续运行与单次补全的预算归属、并发、丢回复和重启验收。
- SDK/wire、序列化和哈希规范；替换现有实例的状态格式可以另行设计，不阻塞先确定公开 API。

实施时同步修改调用方、生成合同和发行资源，在全新临时数据中验证；不得以此文恢复旧接口兼容、迁移真实数据或提前宣称部署完成。当前已实现改造状态以 API 实施记录为准；本文件第 9 节新增 Agent 目标尚待实现。旧五、六命名空间记录保留阶段背景，不代表新增目标已经交付。

当前实现计量说明（Agent 注册制改造后须重新对齐）：`activity.usage` 统计受模块模型预算治理的 `Agent.complete` 预留次数、已报告 token 和 timer 唤醒，不是所有 Provider 会话的总账。`activity.runs` 保留各 Run 的 Provider usage 及其 `scope`；scope 为 session 的累计值不能跨 Run 直接相加。未报告部分不推定为真实零消耗。模块补全计量不依赖可清理的审计记录。

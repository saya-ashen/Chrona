# 可信本地跨平台运行与远程执行应用化方案

日期：2026-11-09。状态：**方案，尚未实施或验收**。

> 归档说明（2026-11-09）：本方案已与《内核语言无关化实施方案》合并为[内核可移植、可信本地运行与远程执行应用化实施方案](../kernel-portability-plan.md)，以合并后的方案为准。本文保留原文供追溯，仅修正归档后的链接。

本文整理本轮平台依赖审查与方案讨论。当前授权范围为编写方案文档，不包括运行时改造、部署、真实设备配对、模型调用或现有用户数据迁移。源码定位以当前工作区为准，不代表其他平台实测结果。

## 1. 决策与目标

### 1.1 已确定方向

1. 去掉强隔离，不再建设各平台的 bwrap 等价隔离后端；目标运行模型为可信本地执行。
2. 保留远程任务：Chrona 可以把任务交给另一台设备，在该设备获准的项目目录内执行并回传结果。
3. 远程执行采用“可选普通应用 + 设备端程序 + 最小通用内核支撑”的方向，不整套固化在内核中。
4. 本轮只形成可供评审的方案；文中的实现选择、阶段与接口均不得当作已经发布的能力。

### 1.2 本方案推荐的删减项

除强隔离外，建议删除硬虚拟内存限制、强制 Shell 包装、核心运行链路中的 Nix 自动供应和浏览器自动下载安装；将 Shell 模块作为可选能力，替换外部 tar 与 Unix 专用通信实现。这些是具体实施建议，不把此前的讨论视作已完成代码改造。

目标是让 Linux、macOS、Windows 的核心服务与本地应用可以原生运行，同时让不使用远程执行的人不承担设备端监管后端的依赖。跨平台支持必须由每个平台的功能验收证明，不能仅由可编译或健康端点可访问推断。

### 1.3 非目标

- 不提供不可信应用的恶意代码隔离，不把 Manifest、路由授权或凭据过滤描述成操作系统隔离。
- 不扩展成通用远程模块宿主、任意插件分发或任意远程命令服务。
- 不新增第二条 Run 队列、第二套 Coding 业务语义或新的不可变内置应用。
- 不因移除隔离而删除身份、授权、预算、取消、停止证据、备份或受控生命周期。
- 不在本方案中迁移现有用户数据或承诺旧协议兼容。

## 3. 删减与保留清单

| 项目 | 目标处理 | 必须同步处理的行为 |
| --- | --- | --- |
| bwrap 和强隔离 | 删除隔离挂载、探测、模式分支及相关启动配置 | 删除 required-isolation 的能力承诺；同步 Pi、Agent 打包产物、健康、测试、文档与发行资源 |
| 旧隔离配置 | 对已设置的 required-isolation 等旧配置明确报错并给出移除说明 | 不把曾要求隔离的配置静默当作可信本地执行；不保留旧隔离实现 |
| ulimit -v | 删除硬虚拟内存限制及 Shell 包装 | 清理 virtualMemoryMb 等字段或声明其移除；旧字段给出明确校验结果；硬内存限制与模型预算不能混为一谈 |
| TS/Python 强制 sh | 直接启动解释器 | TS/Python 可用性不再取决于 sh；显式 .sh 入口仅在 Shell 可用时运行 |
| Nix 自动供应 | 从核心安装与运行路径移除 | 系统程序按需检测，缺失时报告；保留合理的语言锁文件安装流程；移除 GC root 和自动安装副作用前盘点调用方 |
| 浏览器自动下载 | 删除 Nix/固定下载自动获取流程 | 使用显式配置或宿主已安装浏览器；无浏览器仅影响依赖它的功能，不阻止核心启动 |
| 开发辅助 .sh | 改成 Bun/TS 检查与测试入口 | 保留候选检查、离线测试与超时；不以删除脚本为由删验收 |
| 外部 tar | 以进程内实现替换 | 保持私有权限、路径校验、普通文件限制、失败处理和备份恢复闭环 |
| Unix 专用通信 | 以经过三端验证的传输实现替换 | 保持身份绑定、请求边界、取消、断连、HTTP 路由和生命周期行为 |
| /tmp、PATH、venv | 使用平台目录和路径规则 | 包含测试 SDK、构建、预览、Python 环境和发行资源；不只修改一个启动器 |
| systemd/cgroup/flock | 从核心必需依赖中剥离 | 可以作为 Linux 设备端后端保留；其他平台实现各自的监管，能力缺失必须显式报告 |

必须保留：真实 caller、精确授权、凭据处理与日志脱敏、模型预算、单 Run 队列、租约、超时、输出与并发限制、取消、实际停止状态、持久化、备份恢复和受控应用生命周期。

移除强隔离后，应用能够使用运行账号拥有的宿主权限；不能承诺凭据过滤能阻止可信进程自行读取账号可访问的文件。安装与运行材料必须符合这一信任模型。

## 4. 远程执行目标架构

建议普通应用暂名 `remote-execution`，最终名称在合同定稿时确定。它可以作为可选安装包或默认预装包交付；预装不增加权限。Agent 仍是唯一不可变内置应用。

```mermaid
flowchart LR
    C[Coding 等业务应用] --> A[Agent 执行入口]
    A --> K[内核通用准入与 Run 治理]
    K --> R[远程执行应用]
    R <-->|设备专用认证与协议| E[设备端 Executor]
    E --> P[设备上的 Pi 与项目目录]
    R -->|进度、结果、停止报告| K
    K -->|受控结果| A
    A --> C
```

图中的连接表示目标职责和控制路径，不代表已经存在的 API。实现时优先复用现有 Agent 与应用路由，不引入公共 Provider 注册框架或任意应用写 Run 状态的接口。

### 4.1 职责归属

| 主体 | 拥有的职责 | 不应承担的职责 |
| --- | --- | --- |
| Coding | 项目业务选择、会话、轮次、用户指令、结果与 UI 语义 | 设备协议、进程监管、另建执行队列 |
| Agent | 统一执行入口、Pi 适配协作、对调用方的受控执行与控制接口 | 设备配对 UI、设备目录管理业务 |
| 远程执行应用 | 配对、设备凭据、项目映射、在线观察、协议分发、去重、命令与结果收据、重连核对、应用私有设备状态 | 自行授予内核 caller 权限、伪造停止证明、绕过预算或在重连时擅自启动旧任务 |
| 设备端程序 | 本机工作目录、Pi 启动、进程监管、资源能力、事件缓存、取消、状态核对与停止证据采集 | 决定内核权限、在没有有效任务授权时自动续跑 |
| 内核及必要的私有宿主 | 真实身份、调用授权、共享预算、单 Run 队列、占用、取消与生命周期；在明确可信边界接受执行结果 | 固化配对协议、设备发现、项目映射格式、systemd 专用规则或 Coding 策略 |

### 4.2 设备端始终存在

服务器上的普通应用无法直接访问另一台设备的文件和进程。远程设备仍需运行执行程序，可以独立安装或随发行包提供。远程应用停用后，核心本地执行继续可用；不配置设备端不阻止核心启动。

本阶段保留设备端程序的独立形态，不要求在每台设备上安装完整 Chrona，也不扩展为通用远程应用宿主。

### 4.3 认证与通信

- 普通用户访问应用沿用现有 owner/API 鉴权。设备只使用设备专用凭据，不能持有或继承 owner 的全局 API key。
- 当前设备路由有专用认证语义，不能机械迁到要求 owner key 的 `/api/<app>` 代理后面。实施前必须确定凭据验证、入口代理、撤销和应用生命周期如何协作。
- 优先让应用拥有设备认证处理与协议；若现有 HTTP 入口无法承载，只增加解决该认证边界所必需的窄宿主适配，不开放通用免鉴权路由。
- 设备端主动连接服务端、轮询或保持连接的具体方式由协议设计决定；传输中断不构成停止证据。跨设备传输需要明确的受保护传输配置，不能在文档中默认明文跨网安全。
- 内核传给应用的任务授权必须绑定真实调用方、精确任务、目标、预算和有效期；应用不能通过参数替换为任意 cwd 或冒充另一调用者。

### 4.4 应用私有状态与内核状态

设备、项目映射、协议代次、序列号、传输缓存和应用业务收据迁入应用私有存储。共享 Run 的准入、预算预留、取消、占用与最终状态保留在内核。

两者跨进程后不能继续依赖一个共享数据库写事务。迁移必须设计固定请求 key、持久化交付记录、接收收据与重启核对；丢失响应后先查既有收据，不通过新 key 重启同一任务。不得因“业务迁出”而丢弃现有重复执行防护。

## 5. 必须先定稿的通用执行边界

目前认领路径直接读取设备表、核对授权代次并准备远程 assignment，停止恢复路径也直接区分 server 与 device。这些耦合需要以具体场景收缩，不能只把代码移动到应用目录。

实施前需给出以下最小合同及故障状态表：

1. **准入与交付**：一个获准 Run 如何绑定远程目标；应用接收任务不等于设备已启动；哪一条持久化记录防止重复启动。
2. **事件与结果**：进度和结果如何绑定 task/run/attempt、应用身份和执行代次；如何拒绝伪造、迟到或重复报告。
3. **预算与执行约束**：内核预留的模型预算如何约束设备端实际执行；只在最终回传 usage 不足以证明硬预算已执行。不能把该约束推迟到 UI 或仅信任任意应用自报。
4. **停止证据**：设备后端采集什么，哪一可信适配边界验证并接受；普通应用的 `stopped: true` 不是充分证据。若平台无法提供所要求的证据，必须暴露 unsupported/unknown，不伪装为 confirmed。
5. **应用生命周期**：暂停、更新、删除应用时如何撤销新任务授权、处理已运行任务和保留恢复记录。
6. **身份变化**：应用版本、设备配对代次或运行实例变化后，旧授权如何拒绝、既有任务如何核对。

这些接口优先保持私有、窄且基于现有 Run 机制，不增加公共内核命名空间。若无法保持现有预算或停止语义，应记录具体缺口并先解决，不能宣称拆分完成。

## 6. 故障与生命周期规则

| 情况 | 必须发生的行为 |
| --- | --- |
| 设备离线且任务未交付 | 排队或按队列有效期结束，不在其他设备自动执行 |
| 已启动设备断连 | 状态为无法确认；保留占用，不从断连推断停止 |
| 取消响应丢失 | 查询固定命令收据；停止未确认时不释放占用 |
| 应用进程重启 | 恢复协议状态与任务核对，不重新启动已经接收的 attempt |
| 设备端重启 | 先核对遗留任务和进程身份，再接受新任务；恢复不等于自动续跑 |
| 设备撤销或授权到期 | 阻止新的启动与敏感操作，已运行任务进入取消和核对流程 |
| 应用暂停或卸载 | 禁止新分发；先停止并核对已有远程工作。无法确认时阻止声称完成卸载或删除唯一恢复材料 |
| 旧实例回传结果 | 校验任务绑定、代次与收据，拒绝越权覆盖；保留可核对证据 |
| 结果已接收但确认丢失 | 重传返回同一固定结果，不重复记账或执行 |

未知状态不无限制自动重试，不假定远程系统提供恰好一次执行。保留证据、固定 key 和保守占用用于控制不确定性。

## 7. 本地跨平台运行设计

### 7.1 启动与进程监管

TS/Python 直接启动解释器。统一需要的行为为启动、超时、取消、进程树清理、退出观察和能力报告。实现可以因平台不同，但不能把直接子进程退出当作整个任务树已停止。

Linux 可保留设备端的 systemd 后端；Windows Job Objects、macOS 的进程监管方案作为候选，需要分别验证 Bun 集成、子进程逃逸及父进程异常退出行为，本文不承诺已有可用实现。普通本地运行不要求 systemd 262；Linux 设备端是否继续锁定该版本，待后端验收后确定。

删除硬内存限制后，健康和配置不得再声称限制已生效。模型 token 预算、工具调用上限、运行时限、输出上限和并发上限继续独立执行。

### 7.2 本地 IPC 与 HTTP

候选方式包括各平台本地 IPC 或仅监听 loopback 的连接。以三端实际支持和最小改动为依据定稿，不因名称统一而假设 Bun 所有传输能力一致。

若改用 loopback，需要每实例不可猜测凭据、目标实例绑定、启动就绪握手、监听地址限制、大小限制和断连处理；不能仅凭“来自本机”授予 caller 身份。内部凭据不得注入应用自述 caller 或输出日志。

模块 HTTP 继续经过现有受控路由与代理；内部监听端点不成为绕过鉴权的公开入口。预览、构建启动检查、SDK testing 与生产运行必须共用同一合同。

### 7.3 路径、工具与备份

使用 os.tmpdir、path.delimiter 和平台解释器布局。依赖按功能检测，TS 应用不因缺少 Python、Shell、浏览器或 Nix 而不可用。

进程内备份替代 tar 时，优先维持现有受限 ustar 读取合同，避免无必要地变更恢复格式。覆盖普通目录、文件、空目录、长路径边界、恶意路径与特殊文件；不因跨平台而放松恢复路径校验或私有存储要求。

## 8. 实施阶段与交付

### P0：合同与删减清单

- 固定移除模式、配置、Manifest 字段、发行资源与调用方清单。
- 完成远程执行的授权、预算、状态、收据、认证入口和生命周期设计。
- 确定本地与设备端各平台停止能力的验证办法。
- 交付：合同草案、故障状态表、源码影响表和可执行验收用例清单；未定稿项不得用空适配器掩盖。

### P1：可信本地运行与工具减依赖

- 移除 bwrap/required-isolation、ulimit 和 TS/Python 强制 Shell。
- 收缩 Nix、浏览器自动获取和辅助 Shell 脚本。
- 修复路径、解释器与环境构造；完成进程内备份。
- 同步 Agent 生成产物、资源、配置、doctor/health、AGENTS 与运维说明。
- 交付：本地功能行为验证；此阶段不据此宣布三端完整支持。

### P2：本地通信与监管跨平台

- 完成 IPC、HTTP、预览、测试 SDK 与构建检查的一致实现。
- 完成各平台进程清理、取消与异常退出处理。
- 交付：三端本地验收矩阵与未支持能力说明。

### P3：远程应用与设备端拆分

- 先抽出服务器与设备端共用的工作目录准备、锁定和清理代码，保留本地 Coding。
- 将设备协议、凭据、配对、映射和业务记录迁入普通应用，提供必要的设备认证入口。
- 改造内核直接认识 Executor 的认领、路由、恢复和完成路径，保留最小可信执行支撑。
- 设备端独立打包，Linux 监管后端与核心解耦；新增其他平台后端前保留明确的能力限制。
- 交付：无远程应用的核心、本地 Coding、已安装远程应用与实际设备端四种组合的验证证据。

### P4：三端远程验收与旧链路清理

- 覆盖三端设备执行、断连、取消、重启、撤销和应用更新/卸载。
- 删除被替代的设备专用内核协议、直接数据库耦合、配置和打包残留。
- 发布矩阵单独列服务端与设备端支持情况；一个平台的客户端通过不能证明全部组合通过。
- 交付：准确命令、修订、平台、通过项、失败项及限制；不以历史 smoke 代替本轮验收。

## 9. 验收标准

### 9.1 核心与本地应用

- 核心启动、本地 TS 应用与本地 Coding 不依赖 bwrap、systemd、flock、Nix、外部 tar 或 sh。
- Python/Shell/浏览器只在对应功能使用时检测；缺少可选组件不影响其他功能。
- 模块安装、候选检查、启动、调用、HTTP、预览、停止、更新与服务重启在三端验证。
- 超时、取消、子进程产生后取消、父进程异常退出均有真实进程行为证据。
- 备份恢复往返及路径与权限边界通过；所有自动化验证使用临时数据。

### 9.2 远程执行

- 无远程应用时本地功能正常，内核启动不探测设备监管工具。
- 设备端无 owner key；配对、撤销、项目目录授权与原 caller 绑定正确。
- 任务、命令和最终结果的丢失响应、重复消息、乱序及旧代次消息不能触发重复执行或覆盖。
- 设备断连、应用重启、设备重启、服务端重启后先核对，不把未知停止标成成功。
- 预算不能仅靠最终自报；实际执行路径有约束证据。
- 应用更新、暂停和删除不能遗留被误认已停止的远程任务或删除其唯一恢复记录。
- Coding 和其他业务调用方继续共用同一 Run 队列与授权边界，不增加一套设备专属任务系统。

开发阶段先用临时数据库、假设备传输和真实本地测试进程覆盖故障。真实设备、模型、账号及部署验收需要单独明确范围；方案文档不授予这些操作权限。

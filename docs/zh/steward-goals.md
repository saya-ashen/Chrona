# Chrona 设计目标：主动、灵活的个人管家

状态：2026-10-15 用户定稿。本文是 Chrona 产品目标的**最高依据**；
[personal-steward](personal-steward.md)、[steward-agent-work](steward-agent-work.md)、
[steward-chat-loop](steward-chat-loop.md) 记录实现与现状，与本文冲突时以本文为准，按本文逐步收敛。

## 1. 定位

聊天里随时能找的个人管家 + 网页上可掌控的事务中心 + 能持续办事的后台 Agent 服务。

> 交代一次，记得住；能做的事情主动推进；有重要变化及时告诉我；
> 回来查看时，清楚发生了什么、成果在哪里、还有什么没解决。

不是 workflow 编辑器，不只是成果仓库，也不是固定命令菜单、服务监控模板或工单机器人。
最终目标：用户用自然语言交代事情，Chrona 选择合适的方法把事情办好、持续照看，
而不是让用户管理一个 Agent 执行系统。

## 2. 核心对象：一切皆事务

用户只需要理解一个概念：**事务**。

- 一次性请求是短事务；持续关注是带检查节奏的事务（即“委托”只是事务的一种照看方式，不是并列概念）。
- 成果、跟进、待决定、相关消息、工具、脚本、面板都**归属某个事务**；事务结束时，其工具随之停用或由用户决定保留。
- Work / Attempt / Assessment 等是内部执行记录，只在事务的技术详情中出现，不作为一级概念暴露。
- 不是每句话都成为事务：简单问答、闲聊不落事务。

## 3. 自然交流

- 用自然语言交代需求，不要求学习命令、填写表单或记回复码。回复码、内部状态和 ID 只作为后台机制或备用入口。
- 能区分新需求、补充信息、修改意见、普通提问和闲聊；理解“再加上这个”“换个方向”“刚才那件事暂停一下”。
- 只有同时存在多件事、确实无法判断指代时，才简短澄清。
- 长任务先简短确认、后台处理、完成后主动通知；不反复发送模板化回执和技术声明。

**聊天入口**：Chrona 使用独立 QQ Bot，与 Hermes Bot 分开。白名单私聊中的每句话都交给 Chrona 理解，
不需要 `/chrona` 前缀。Bot 是 Chrona 的消息入口和通知出口，不是另一个需要用户协调的系统。
现有 Hermes 插件路径在独立 Bot 可用后退役。

## 4. 按需选择处理方式

| 需求 | 处理 |
| --- | --- |
| 简单问题 | 直接回答 |
| 一次性调研 | 实际查证，给出结论、依据和来源；值得保存时形成网页成果 |
| 模糊或复杂目标 | 只问真正影响结果的关键条件，逐步推进 |
| 持续关注 | 形成带节奏的事务，持续检查、判断变化、必要时通知 |
| 重复且规则稳定 | 复用现有工具，或生成脚本自动化 |
| 需反复比较、查看、填写 | 生成面板或表单 |
| 不值得自动化 | 直接完成，不为展示能力而造工具 |

- 处理方式由 Agent 根据目标、现有能力和实际收益判断，**不按关键词分派到硬编码模板**。
- 判断**可见、可纠正**：事务中能看到“打算这样处理，因为……”；用户一句“别建监控，查一次就行”即可改变，并记住这一偏好。
- 自动化的经验门槛：同类手工劳动第三次出现时才主动建议工具或脚本。

## 5. 真正能办事的 Agent

Agent 需要能：理解目标并读取相关背景、已有成果和反馈；自主规划、选择工具、执行多步工作；
检索、读取已接入来源、分析比较、整理和发布成果；缺信息时提问，得到补充后接着原事继续；
遇到问题时诊断并调整方法，而不只是返回“不支持”；保存进度，中断后可续；
根据反馈**真正修订**成果；必要时制作脚本或面板。

只调用一次模型返回分类 JSON 不算 Agent 能力。复用 Pi 等成熟 Agent 的规划和工具能力，
不重建重型 DAG／节点 workflow 引擎。

## 6. 主动性

在已交代的事务和获准的信息范围内，Chrona 应：持续跟进未结束的事；关注重要变化、临近期限、
阻塞和长期无进展的事项；发现值得提醒或行动的信息并给出具体建议；识别重复劳动并建议更省事的做法；
判断什么时候继续做、什么时候问用户、什么时候保持安静。主动性建立在真实上下文和实际工具能力上，
不是几个固定条件触发的提醒模板。

**打扰预算**（默认值，用户可调整）：

| 级别 | 适用 | 方式 |
| --- | --- | --- |
| 立即推送 | 需要用户决定、重要故障或阻塞、长任务完成 | 聊天私信；每天最多 5 条，超出部分转入日报 |
| 日报汇总 | 一般变化、进展、建议 | 每天一条，无内容则不发 |
| 仅网页 | 低价值变化、技术细节 | 只在今日 / 事务页显示 |

- 安静时段 23:00–08:00 只推送紧急事项。
- 用户拒绝过的建议，30 天内不再就同一主题提出；连续被标为“没用”的通知类型自动降级。
- 每条主动消息都要回答：发生了什么、为什么重要、建议做什么。

## 7. 自主权与权限

参考 Meta Muse（Sentinel）、OpenAI dots（Custom Rules / auto-review）与 Hermes（危险操作审批）的做法：

1. **模型只提议，确定性策略决定**。Agent 提出动作，由 Chrona 的权限层判定允许 / 询问 / 拒绝；
   外部文本只是数据，不能授予权限。模型无法修改策略。
2. **每类动作四种模式**：直接做 · 预先授权后直接做 · 先问再做 · 交还用户（Chrona 永不做）。
3. **默认分级**：

   | 模式 | 动作 |
   | --- | --- |
   | 直接做 | 只读检索、读取已授权来源、在 Chrona 内写入（事务、进展、成果、跟进、建议） |
   | 做完告知 | 为已交代的事务设定检查节奏、启用声明式面板 |
   | 预先授权后直接做 | 已经用户批准的脚本版本在沙箱中运行；已批准范围内的同类操作 |
   | 先问再做 | 首次运行或修改后的脚本、对外发送消息、修改外部系统、购买、删除数据、接入新来源或扩大权限、分享信息给第三方 |
   | 交还用户 | 修改密码与凭据、安全设置、支付凭据 |

4. **授权粒度**：批准时可选“仅这次 / 这件事务内一直允许 / 拒绝”；授权可限定到来源、动作、事务和时间，
   读写分开授予，随时可在网页查看和撤销。
5. **避免审批疲劳**：已授权的低风险动作不再重复确认；只有真正敏感的动作才询问。
6. **凭据不进 Agent**：Agent 只见占位符或受限工具，凭据由系统在边界注入。
7. **全量审计**：已做的和计划要做的都可追溯；暂停 / 撤销立即阻止新动作，已发生的外部效果如实记录。

## 8. 记忆

- **事务内上下文**：原话、补充、决定、反馈、成果版本——交代一次，不必重复。
- **长期偏好**：用户明确说过或反复纠正得出的偏好（通知习惯、处理方式偏好、拒绝过的建议）。
  可在网页查看、修改、删除；Chrona 引用偏好做决定时可说明依据。
- **不记**：凭据、与事务无关的外部私人信息。

## 9. 消息与外部来源

聊天是日常入口。可接收已接入、获准使用的服务信息，归入对应事务；同一件事的消息、进展、
成果和后续跟进聚合在一起，而不是散落在聊天记录里。来源的授权、读写范围、同步状态和遗漏风险在网页可见。

## 10. 网页：事务中心，不是执行日志控制台

用户应能迅速看清：哪些事在推进、哪些需要自己决定、有什么重要变化、已经产出了什么、
接下来会发生什么、如何补充 / 修改 / 暂停 / 结束。

- **今日**：重要变化、待决定、临近事项、建议、成果。离开多天后打开，第一屏就能回答“发生了什么、要我做什么”。
- **事务**：目标、背景、相关信息、进展、成果、下一步、照看方式（节奏、最近检查、暂停与结束）。
- **连接与工具**：可用来源、工具、脚本、面板、授权与偏好。

成果是可阅读、可使用、可修改、可继续加工的内容，不只是标题、状态和原始日志。技术执行详情放在次级位置。

## 11. 后台复杂性由系统承担

Chrona 负责事务、进度、成果、调度、通知、持久化、去重、恢复、权限与投递；Agent 负责理解、规划和工作。
这些复杂性不能变成用户每一步都要遵守的操作协议。

- 用户已明确交代的常规工作，不反复确认；真正有歧义、缺关键条件或涉及敏感操作时才询问。
- 做不到时说明具体缺什么，并尽量完成能做的部分。没完成不能冒充完成，但日常交流不充斥防御性声明。
- **成本有界**：每件事务有运行与调用预算，检查节奏有下限；超出预算时降频并告知，不静默停止，也不无限消耗。

## 12. 验收

验收标准是真实使用是否省心，不是测试数量、接口数量或部署成功。

**场景**（至少）：

1. 没有专门模板的需求能被理解并实际完成。
2. 简单问题直接回答，不机械创建事务。
3. 连续补充和修改意见能接上原事务，不要求编号。
4. 调研有真实来源、可用结论和网页成果。
5. 长任务不用催，完成或遇到重要问题会主动反馈。
6. 持续事务能跟进，也能用自然语言暂停和结束。
7. 重复工作能合理选择现有工具、脚本或面板，而不是一律建监控。
8. 用户离开再回来，不翻聊天也能快速理解进展。
9. 反馈“不对”之后，成果被真正修订。

**失败场景**：Agent 中途崩溃或服务重启后能续上；外部来源不可用时如实说明并降级；
敏感动作在需要确认的地方确实停下；超出打扰预算的通知被合并而不是丢失。

**方法**：维护一套评测场景集，每轮验收**加入未写进开发任务书的新需求和连续对话**，旧场景保留做回归。

**观察指标**：

- 简单问题被误建为事务的比例；
- 需要用户提供编号或重复交代的次数；
- 主动通知被标为“没用”的比例；
- 需要决定的事项从产生到用户看到的时间。

## 13. 非目标

- workflow / DAG 编辑器、节点编排引擎；
- 固定命令菜单与关键词模板路由；
- 只为展示能力而生成的工具；
- 多用户协作（当前为单一 owner）。

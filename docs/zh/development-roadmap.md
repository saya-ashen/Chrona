## 3. 开发前先处理的冲突与缺口

### 3.1 内置应用可变性：已裁定

2026-11-08 用户确认：**web、mcp、files、notify、events 允许受检定制；Agent 保持不可动态替换。** 五应用可经已有检查流程 build/propose/group/activate/update/rollback，仍禁止动态 remove/install；名称和内置身份保留，不能借定制取得内核或 Agent 权限。普通登记只首次可信 seed，已有 active 定制不由发行自动覆盖；显式上游更新走受检流程。

此决定符合当前 `module-identity.ts` 操作守卫和 `module-builtin.ts` 登记路径。本轮同步 AGENTS、当前架构、产品目标和专题阅读提示，旧 P0/M1 正文保留历史；没有修改运行时或推断自动回滚已扩展并验收。它不再阻塞工作台开发。

### 3.2 发行种子的数量与可更新来源

当前 `resources/module-git/lock.json` 有十二份种子，包含 Agent。只有 files、events、remind 的 `repository` 非空；web、mcp、notify、agent、qq、mind、memory-local、coding、editor 为 null。此处只说明本地锁定元数据，没有联网核实远端仓库的实时状态。旧文档“十一项都已发布”的说法不能用于承诺当前版本可从上游更新。

处理：区分离线 bundle 可用、源码曾经公开、当前发行 commit 已经公开并核验三件事；在实际发布任务中核对种子、构建脚本、许可通知、公开提交及锁文件。不要为修正文案伪造 repository 或发起推送。

### 3.3 验收范围需要跟随后续变更

V1 曾完成真实模型验收，随后又有 Agent 独立进程、应用会话迁移和编码页面改造。保留旧证据，但不能写成整个当前树已再次完整验收。尤其需要核实入口回复的截断快照、完整附件交付、重启后的会话与投递，以及当前种子与源码的一致性。

## 4. 后续开发主线

### A. 编码与多入口体验：当前首要主线

最新范围以[编码工作台实现评估](coding-workbench-implementation-assessment.md)为准：本机目录从页面接入，包含非 Git/空目录；普通编码直接写入并可跨轮继续，差异和人工验收不是生效门槛。W0 与 W1 已完成开发集成，证据及剩余边界见[开发验证记录](coding-workbench-validation.md)。下一步是真实使用验证与反馈，W2 仍单独评估。

**先调研并交付可日常使用的编码页面，再继续架构演进。** 当前 coding/Agent 已有创建、执行身份、事件/快照、追加输入、问答、取消与停止证据、成果捕获/验收；另有业务会话、固定位置、父子工作、独立 worktree 和清理接口。基础网页只使用其中一部分。详见[工作台当前能力与后续](coding-web-workbench.md)。

| 阶段 | 可审查交付 | 依赖与验收 |
| --- | --- | --- |
| W0：调研、范围与交互比较，已完成 | [参考项目调研](workbench-reference-research.md)、认可的交互原型及普通编码范围确认 | 选择轻量侧栏与对话主区，不以 Orca 或固定三栏为前提 |
| W1：连续本机编码，开发集成完成 | 热登记任意已有目录、对话切换与跨轮续接、增量回复历史、原生问答、停止证据、可选差异；刷新恢复 | 受控后端与真实页面浏览器检查通过；真实模型/项目验收单独记录，不强制成果接受 |
| W2：工作树与跨入口接续 | 页面接入既有 work/placement、独立 worktree、父子工作和显式清理；从其他入口查看及控制同一工作 | 先统一 v1 单项页面、v2 工作图与 sessions 的业务引用，不造第二个工作库或调度器；结果接受、代码合并、工作树清理分开 |
| W3：真实使用反馈，下一步 | 隔离项目中完成默认空间直接发送/添加项目→项目分组→直接编辑→补充/答复→停止/完成→继续下一轮→离开返回；按需查看 diff | 自动验证使用受控后端；真实模型另按明确授权验证。跨入口完整接续仍需单独验证；修复实际阻塞，再确定架构任务 |

2026-11-08 后续已完成[全站 Web 外壳和应用私有组合组件](web-components-and-shell.md)的开发集成：统一内置/登记页主题导航，Coding 问题卡与输入区由应用组合公共组件。源码验证不表示本次已更新部署或完成真实模型使用验收。

各阶段可独立交付；W1 可先成为能使用的页面，W2 再接入复杂工作。2026-11-08 用户进一步要求先调研，指出 Orca 的界面过于复杂且架构不同；以[参考项目调研](workbench-reference-research.md)比较具体交互，撤回 Orca 风格和固定三栏作为前提。完整文件编辑器、交互终端、自动提交/合并、通用远端宿主和项目同步不列入首版。

界面与业务仍由 coding 提供，web 仅增加可复用布局、交互和必要进度展示；Web、MCP、editor/QQ 继续经真实调用方和同一业务工具访问，不新增入口私有执行队列。Neovim/外部 Workbench 的兼容性需要在对应仓库核对；当前代码基础足以开始页面，但不等于跨入口体验已经验收。

### B. 个人管家产品闭环：持续主线

来自[设计目标](steward-goals.md)的自然交流、主动跟进、长期偏好、来源接入与成果修订仍然有效。已有 mind、memory-local、notify、files、入口会话等机制不等于以下体验已通过产品验收。

| 子目标 | 下一项可执行工作 | 完成判断 |
| --- | --- | --- |
| 对话能接续与纠正 | 验证新需求/补充/暂停/修订、多轮等待、应用会话重启及正确接收者交付 | 加入未写进实现任务的新需求，用户不必重复交代或给内部编号 |
| 完整成果交付 | 核对入口依赖截断 transcript 的限制，设计完整文本/文件引用与继续加工路径 | 长回复不因快照截断冒充完整；文件可读、可授权访问、可修订 |
| 主动跟进与克制通知 | 场景验证 mind → Agent → 应用 → notify 的变化判断、预算、静默、暂停和拒绝偏好 | 有变化才提醒；用户可结束；未知结果不自动重放 |
| 记忆、来源与偏好 | 以一项实际需要验证保存/召回/纠正/删除及来源权限 | 能解释引用依据、不记录凭据、不越权读取，来源不可用如实显示 |
| 应用首页与今日 | 以实际数据验证待决定事项、成果与下一步，保持应用拥有页面和业务聚合 | 用户离开后回来可快速看懂进展，无须翻技术日志 |
| 按需生长与修复 | 用一次外置应用新增/修改验证需求→构建→检查→启用→使用→反馈 | 解决实际重复需求；不把所有经验或一次工作强制做成应用 |

先维护一组产品场景及观察结果，按失败选下一项开发；不将所有长期目标宣称为缺失，也不为每项预建新模块。一般产品改善可以与工作台并行；依赖新授权和产出协议的改动等待对应契约。

### C. 调用治理与结果链路：工作台之后按需推进

先完成可使用的工作台；不将通用委托、通用 Run 或产出协议作为其前置条件。现有治理路径继续使用，不新增业务绕行。详案：[调用上下文路线](call-context-run-artifact-roadmap.md)。按顺序交付：

1. **调用 P0：最小契约。** 明确发起人、直接 caller、执行者、授权来源；按工具显式委托、继续委托和使用自身权限的边界；异步/并发绑定、失效授权、旧 `uses/visibility` 迁移及首阶段 Run 关联。输出路径清单、接口草案、拒绝用例和迁移映射。
2. **调用 P1：Agent 接入。** 用“业务模块 → Agent → 目标模块”证明可信上下文及权限链路。统一目录与执行授权，在临时数据和真实 SDK/fake Pi 下验证身份、预算、超时、取消、跨工作区拒绝和并发隔离，再删除专用入口重复治理。
3. **调用 P2：通用 Run。** 在现有唯一调度基础上增加必要 Call/父子/Attempt 关联，确定同步与附属异步完成、独立任务派生、取消和未知停止语义。先服务一个实际任务，不普遍引入持久工作流。
4. **调用 P3：可查询结果与依据。** 业务结果附完整性、警告和受权详情引用；详情能定位失败来源且不泄露敏感内容。
5. **调用 P4：产出复用。** 在真实数据链路中显式绑定带类型、版本及来源的输入，由接收者在副作用前接受/拒绝，转换显式执行；跨 Run 复用不继承权限。

P2–P4 是按需求推进的后续阶段，不与 P0/P1 打包成一次不可审查的大改。既有 coding 成果捕获与接受机制是可复用基线，不另造第二套成果权威。

### D. 发行、旧数据与生产升级：独立交付线

已有开发成果尚需形成可发行、可回退的完整版本。工作顺序：

1. 按已确认的五应用定制规则核对生命周期与回归，核对当前源码、生成资源、十二份种子、许可和上游锁定状态。
2. 对最终选定版本执行相应自动检查、发行构建、fresh SQLite 安装及所需环境验证；记录 Chrona、执行器和外部 Workbench 的兼容版本。
3. 只读盘点旧实例的内置定制、外置模块、代码、数据、凭据声明、日程、会话、未知执行与位置占用；历史名单不能代替实际清单。
4. 设计一次性转换与保留/归档策略，在数据副本演练，检查备份/恢复和停止窗口；不将旧模式兼容桥加回正常运行架构。
5. 将可审查的迁移报告、最终制品和回退步骤交给用户，再按具体授权执行真实迁移、部署、账号连接及公开发布。

此线可以先做隔离环境准备，不要求完成远端宿主或全部 P2–P4 才能发行；如果选择先发行当前本机范围，必须明确哪些新路线未包含。

### E. 通用远端宿主：保留、暂缓

[统一模块协议方案](unified-module-runtime-plan.md)的 U3/U4 保留为远端专题。先冻结认证、版本、固定部署、调用身份、journal/ACK/对账、撤权、未知停止、制品安装和大文件边界，再用一个不 listen 的普通模块验证，最后收敛既有专用设备协议。

依赖本机身份和操作语义稳定；不要求等全部产出协议完成，也不阻塞近期本机产品与发行。现有 executor 设备协议不是通用模块宿主。内核集群、自动跨机迁移、多租户、分布式事务、自动项目同步、插件市场及重型 workflow 语言继续不列入近期。

## 5. 当前开发顺序与架构衔接

| 顺序 | 可审查交付 | 前置条件 |
| --- | --- | --- |
| 已完成决策 | 五个内置应用受检定制，Agent 不可普通替换；同步当前规则 | 不改现有运行行为 |
| 首个产品里程碑 | W0 调研与场景方案比较，再做 W1 可使用的服务器编码工作台 | 现有 coding/Agent/Web；页面结构尚未冻结，只补实际界面和接口缺口 |
| 第二个产品里程碑 | W2：已有 worktree/工作图与多入口接续 | 稳定业务引用、调用者归属与版本兼容 |
| 使用与发行 | W3 真实使用反馈；按需并行收口本机发行 | 选定版本的验证和对应真实环境授权 |
| 后续架构 | 调用 P0→P1；实际需要时再 P2→P3→P4 | 用工作台暴露的具体授权、执行或结果问题驱动 |
| 后续远端 | U3→U4 | 本机契约稳定和独立设备/传输验证 |

两条路线没有顺序上的冲突。工作台的会话、作品和选择状态是应用业务；未来 Run/Call 是执行治理事实，不应把业务主键直接等同于 Run 主键。coding 内已有 Agent 映射层，后续原语变化优先在此适配。既有父子工作图不是通用 Call 树，成果依赖也不授予权限。当前停止、未知状态占用、预算和真实 caller 继续保留；若出现具体归属或恢复缺陷，在工作台范围内先修复，不要求提前完成整个架构路线。

# Agent 编排工作页面：内容、交互与持久化提案

> 2026-09-17 · 讨论稿，未批准实施／迁移／部署／扩权。
> 用户认可第二轮配电脑参考页的易用性方向，但明确不能因此移除高级能力，**日程必须保留**。本提案回答 Agent 如何生成类似页面，以及页面操作如何写入后端。
> 体验参考：[配新电脑](../prototypes/pc-planning/README.md)。产品边界仍由 [产品架构](product-architecture.md)、[独立成果](../en/work-results.md) 与现有 Goal Workbench 规则约束。

## 结论

推荐以现有 `@chrona/ui-protocol`／json-render 为基础：**语义内容＋可组合页面描述＋版本绑定表单＋受限动作协议**。

Agent 编排内容与输入结构；Chrona 负责可靠存储、统一渲染、身份、版本、权限和动作后果。不是让 Agent 写一份拥有宿主权限的网页，也不是每个具体场景新增一个硬编码模板。

AG-UI 可以作为未来实时交互传输适配；不作为保存页面和用户数据的核心契约。HTML 保留为隔离的特殊成果类型，不作为默认有后端写入权限的页面。

## 已核对的现状

- `packages/ui-protocol/src/schema.ts` 已定义 JSON UI 树。
- `catalog/components.ts` 已有 shadcn 基础、结果章节、比较、表格等组合能力；不必重造通用组件基础。
- `document/validate.ts` 已做结构、组件属性、引用和部分 action binding 校验；**这不是新交互的身份／能力／数据库写入授权器**。动态表达式也不能因为通过这一层就任意读写数据。
- `actions/actions.ts` 当前包含 `accept-plan`、`dispatch-execution`、`submit-checkpoint` 等托管用途动作。不能把这一整套目录原样开放给新外部成果页面。
- B1–B3 独立成果有不可变版本、审阅、文件及确定性基础展示，但不是完整的外部 Agent 交互页面持久化闭环。
- Goal Workbench 已定义并实现 Form 版本与独立 Submission，以及隔离 Page。复用其语义与可复用代码，但不能为了让普通工作有表单就伪造 Goal、Plan 或 Run。Goal 正式资产晋升也不能自动发生。
- 配电脑原型只是本地内存样例，不含真实后端写入。

## 技术选项不是互斥替代品

| 能力 | 适合的位置 | 不能单独解决的问题 |
| --- | --- | --- |
| AG-UI | Agent 与前端的事件、消息、状态增量传输 | 持久化、重连后的权威状态、权限、审阅与长期版本 |
| A2UI | 跨客户端的声明式组件／数据绑定描述 | Chrona 的具体记录、命令、身份及版本语义 |
| 现有 json-render | Chrona 已有声明式页面渲染与 catalog | 仍要补工作范围表单、持久化动作、资源授权和更新规则 |
| HTML／JS | 隔离的特殊交互成果、可视化小工具 | 不能直接接触宿主 DOM、凭据或任意后端 API |

一开始就换 A2UI 的收益尚不足以证明迁移必要；如果以后需要多个客户端共享标准，再用适配层接入。传输协议的消息到达也不代表服务端写入成功。

## 四层，而不是一份混合 JSON／HTML

### 1. 工作数据与成果

保留有意义的背景、约定、事实、判断、数据集、来源、价格时间、产物和未决问题。数据可以被 Agent 读取、检索、导出，即使没有这份页面也有用。

沿用稳定 Task 身份和既有独立成果版本；页面不是新增一套平行的外部 Task／Result 系统。无模型可用时仍能查看基础内容与已有输入。

### 2. 页面与表单定义

Agent 可定义章节、顺序、折叠、比较视图、表格列、筛选、输入字段及只读表达式。引用已授权的数据，不用在每个组件复制一份业务事实。

表单定义有固定版本、稳定字段 ID、类型、选项、校验、说明与用途。先实现 JSON Schema 的有界子集，不允许远程引用、无限递归、任意验证脚本或无限正则计算。

不要仅开放“电脑采购卡”“会议卡”两种死模板；组合级表达能力应覆盖新场景。新通用组件仍由开发者实现、测试、纳入 catalog，不能由成果携带未经审查的组件代码。

### 3. 用户输入与持续编辑内容

用户笔记、草稿、表单回答、选择和显式决定不存入不可变的旧成果正文。

- 表单回答绑定工作、具体表单定义版本和字段身份；借鉴现有 Form/Submission。
- 持续笔记有自己的修订与当前值，历史可追溯，不要求每次输入重新发布 Agent 结果。
- Agent 更新排版或提交新报价，不得清空用户笔记或静默改写回答。
- 输入期间不自动替换当前版本；出现新版本时提示切换。
- 改字段含义、删除选项不自动迁移旧答案；保留原回答与原定义，可另行明确映射。
- 自由文本写“下周买”不自动成为日程、执行授权或订单。

具体数据库字段与迁移不在本提案中直接确定；先核对可复用能力和版本边界，再形成实施契约。

### 4. 产品命令与权限

表单保存走受限产品命令，不是任意 URL／HTTP method／SQL／JSON Patch。服务端验证真实操作者、工作范围、表单身份、字段类型、权限、版本和 requestId，再事务提交并返回回执。

Agent 生成的 action 字符串是意图，不是能力凭据。可用能力由宿主和服务端决定；不能由 spec 自己声明已经获得。

## 三档交互

1. **本地展示**：折叠、切换比较方案、排序、筛选、合计等。不调用 Agent、不做后端写入。表达式只允许注册的有界纯函数，不执行生成的 JS；可信合计不采纳被篡改的客户端计算值。
2. **普通内容写入**：保存笔记、提交表单回答、记录用户选择等。显式保存或明确范围的自动保存，服务端确认后才显示已保存。重试用原 requestId；版本冲突保留输入并要求对照处理，不能盲换 revision。
3. **有权威／副作用的操作**：安排日程、接受成果、执行／取消、权限批准、外部发送或购买。使用 Chrona 固定控件和既有领域命令。AI 只能提供建议／上下文或请求宿主展示一个能力入口，不能控制授权语义、伪造确认或隐藏后果。

不把每一次本地折叠或保存笔记交给 LLM 处理；模型不在线也应能打开页面和保存已支持的输入。

## 配电脑示例

Agent 发布的东西：

- 需求与约定；配置数据集；两条带来源和核价时间的购买路线。
- 页面描述：简介 → 配置摘要／完整表格 → 比价 → 商量笔记。
- 表单定义：`buy_timing`（未定／近期／稍后）、`discussion_note`（文字）。字段是页面内容，不是底层 Task 状态。
- 安全链接引用；是否允许展示／打开由宿主核查，不能加载不受限的远程脚本、图片或携带凭据的 URL。

用户点击“记下来”的数据链路：

```text
用户输入
  → 浏览器本地草稿和校验
  → 宿主绑定的“保存这份表单回答”命令
  → 后端重新验证身份、工作／表单版本、字段及修订
  → 事务保存回答、必要修订和幂等回执
  → 回传持久化值和新 revision
  → 页面显示已保存，首页投影反映已知选择
```

这里不自动核价、不通知 Agent、不触发订单，也不自动改 Task／Goal 完成状态。

几天后另一个获授权的 Agent 可以读取同一工作、配置版本、回答和新的修改意见，确定继续范围后再工作。并不需要常驻会话或保存整段聊天。

## 日程和高级能力保留在哪里

- 日程保留稳定一级入口，不藏成难以发现的高级菜单。
- 每件事也有产品控制的“安排时间”入口，打开既有日程编辑器；无需 AI 生成另一套日期／时区／冲突逻辑。
- 表单中的日期字段只是该表单内容。只有经过明确的日程领域动作，才写入 WorkBlock／dueAt 等相应数据。
- 真实托管任务保留执行状态、输入、审批、暂停／取消及恢复入口，无法观测的外部 Agent 不显示这些假控件。
- 普通使用以事情和正文为入口，复杂能力按需出现；这不等于删除原本的能力。

## HTML 的位置与风险

纯 HTML 很适合静态稿、交互图和小计算器，但不能充当默认的宿主级应用接口。

若以后开放：独立来源或 opaque-origin iframe、严格 CSP、最小 sandbox、默认禁止网络／父 DOM／宿主存储／令牌访问。不能认为仅设置 iframe sandbox 就同时解决数据外传、耗资源脚本和权限问题。

如需持久化，只通过宿主的窄桥接协议：校验发送窗口／通道、会话绑定、允许资源／动作、参数、版本、额度和真实授权；不能把 bearer 或任意 fetch 能力交给页面。宿主渲染敏感操作确认，避免“保存笔记”按钮实为购买／删除。

这实际上仍需要同一套持久化与能力层。因此默认采用声明式页面能更快获得一致的移动端、可访问性、字段语义和修订支持。HTML 只作为后续明确隔离的扩展，不是绕过 catalog 的捷径。

## 强 skill 之外还需要什么

- 机器可读能力发现：可用组件、schema 版本、数据引用、表单字段和动作范围。
- 分层文档和少量优质配方：帮助组织信息，不把所有场景锁死。
- 草稿预览与逐路径报错；发布前检查 schema、引用、敏感信息、布局复杂度、移动端和动作绑定。
- 布局修补按稳定 ID 提交，不能整页覆盖用户输入；低风险排版与权限／数据结构变化不同处理。
- 安全保存与重开、冲突恢复、断网后相同意图重试的确定性机制。
- 验证失败仍能读取原有语义内容；合法表单定义有产品生成的基础表单兜底。不能靠调用另一个模型才能恢复用户工作。

## 建议阶段

1. **工作页面契约**：明确内容／UI／用户输入／命令四层，复用现有结果和 Form 语义；确定支持的字段、动作和权限范围。
2. **一条端到端真实持久化切片**：外部 Agent 提交配电脑页面 → 用户填表 → 服务端保存 → 刷新／另设备读取 → Agent 读取回答 → 发布新版且笔记不丢。无 Provider／Run／Goal 前置。
3. **表达能力扩展**：列表、比较、受限计算、条件字段、相关页面；用会议、选型和申请材料等不同场景验证不是硬编码电脑模板。
4. **高级互操作**：有明确需要时再增加 AG-UI／A2UI 适配、隔离 HTML 及显式能力桥接。

授权边界：这次讨论确定方向，不等于批准新增后端写入权限、Schema、迁移、现有凭据扩权或部署。先形成可审议的契约与实施范围；不通过更换前端库掩盖这些问题。

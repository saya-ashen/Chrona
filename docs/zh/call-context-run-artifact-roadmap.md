# 通用调用上下文、Run 与可复用产出：设计及开发路线草案

日期：2026-11-08  
状态：讨论整理与路线建议，尚未冻结接口；不代表已实现、已验收或已部署。

## 1. 结论与建议

这项改造适合作为下一步架构演进方向，但不宜一次性交付完整执行框架。

建议首先统一调用上下文与按工具委托权限，使 Agent 能通过普通模块调用机制使用其他模块；随后按真实任务需要建立通用 Run，再交付带来源、可查询、可在后续调用中使用的产出。

保留内核的最小调用、授权与生命周期机制，`chrona.call` 保持为 SDK 统一入口。业务上下文处理、产出转换、工作流和结果解释由模块完成。不把整个调用机制搬到一个拥有最大权限的内置模块中。

下一步建议交付的是“可验证的调用上下文及 Agent 接入闭环”，而不是要求每个模块调用都立即成为持久化工作流。

### 2.1 已观察到的实现

- Agent 是发行内置的独立 SDK 应用，可以通过 `chrona.call` 调用其他模块。
- Pi 加载 Chrona 随附扩展；扩展发现和注册工具，通过本机 `/api/steward-agent` 接口调用工具。
- 外部用户 Agent 使用内置 MCP 模块的 `/api/mcp` 入口；两种入口在下层复用模块路由，入口身份和授权语义不同。
- 工具桥接入口同时处理 Run 身份、调用预算、期限和执行记录，并非只转发 HTTP。
- 普通 Provider 工具调用与业务模块委托 Agent 的调用存在不同身份路径。后者保留原模块身份，并限制在本次选择的工具范围内。
- 当前模块路由准入主要依据目标工具的 `visibility`；`uses` 是契约，`uses: ["*"]` 还有到达 owner 工具的特殊意义。不能把新设计中的按工具委托权限描述成现有完整能力。
- 已有 `Run` 面向 Provider 执行，包含队列、令牌、租约、期限和工具调用记录；`ModuleRun` 记录一次模块触发的运行；`ModuleInvocation` 记录单次工具调用及异步交付状态。
- 已有调用路径及部分运行关联信息，但还不是所有调用都有通用 Run 归属和持久化父调用关系的完整模型。

## 3. 要解决的问题

1. Agent 已是模块，但 Pi 调用业务工具仍依赖一条包含执行治理的专用入口，需要让它复用通用机制且不损失现有保证。
2. 模块委托其他模块或 Agent 执行时，需要表达“本次工具执行允许使用和继续委托哪些能力”。
3. 跨模块任务需要统一的执行归属、预算、期限和取消语义，以及可追查的父子调用关系。
4. 结果需要附带完整性、警告、依据及详情引用，让用户和 Agent 可以核验并定位问题。
5. 一次调用的产出需要能够显式成为后续调用输入，而不丢失类型、来源和适用范围。

这些需求有共同基础，但不必一次实现。权限委托不以完整 Run 系统为前提；结果复用也不要求原 Run 继续存活。

## 4. 权限路线的选择

### 4.1 路线 A：Agent 持有广泛权限

允许 Agent 以自身广泛权限执行其他模块请求。实现相对直接，但“可以调用 Agent”可能成为一项很大的授权。若接受此模型，应明确哪些 Agent 工具对哪些调用者开放，以及它们允许产生的效果。

此路线可作为产品选择，但不作为本文推荐的通用权限模型。MCP/Web 作为用户入口的授权不能未经分析就复制给普通模块的委托执行。

### 4.2 路线 B：按本次工具需要委托权限（推荐）

这里的委托不是转交模块全部权限，而是由当前工具选择完成任务所需的权限，并在后续调用时继续传递必要部分。

低权限模块调用高权限服务，可以合法产生调用者本身无法直接产生的效果。重点是明确工具允许的效果、授权来源和可继续委托的能力，而不是禁止所有权限组合。

建议采用以下规则，具体表达方式在首阶段冻结：

- 区分模块自身可用权限与本次调用收到的委托权限。
- 当前工具可以显式选取自身有权委托的能力及收到的可继续委托能力，形成下游授权。
- 合并必须保留各项授权来源、范围和限制；不得默认把模块全部权限加入。
- 工具名称只是权限范围的一部分；有实际需要时还应限制资源、操作或参数。首阶段不预建任意策略语言。
- 由内核创建和验证授权引用。模块选择传递及缩小范围，不能自报身份或构造可被信任的权限字段。
- 数据来源、模型文本和执行产出不能自行授予权限。
- 异步交付、重试和代码版本变更时，明确授权有效期、撤销及重新验证规则。

不建议把所有权限简单取并集或交集：并集容易扩大授权，纯交集又无法表达服务使用自身权限完成合法业务操作。需要明确建模的是有来源、有限制的授权组合。

## 5. 概念模型

| 概念 | 定义 | 不应混同的内容 |
| --- | --- | --- |
| Call | 一次具体工具调用，有调用者、目标、输入、状态和结果 | 单次重试尝试、整个业务任务 |
| Attempt | Call 的一次实际执行尝试，用于重试及执行证据 | 新的业务调用或默认获得的新预算 |
| Run | 需要整体管理的一次执行范围，包含入口及所属调用 | 所有会话历史、完整业务工作流 |
| 授权上下文 | 本次调用可使用及继续委托的能力和约束 | 可自由编辑的普通业务 JSON |
| 产出 | 有类型、版本、来源和内容或引用的执行产物 | 执行权限、模型指令 |
| 业务上下文 | 工具理解任务所需的业务资料 | 内核需要解释的通用权限规则 |

### 5.1 Run 与 Call

一个入口 Call 可以建立 Run，后续属于同次任务的 Call 沿调用关系关联。建议的逻辑关联包括 `runId`、`callId`、`parentCallId`；具体字段和对现有表的映射尚未冻结。

```text
Run
└─ 入口 Call
   ├─ 读取资料 Call
   └─ Agent Call
      ├─ 模型执行操作
      └─ 业务工具 Call
```

现有 Provider Run 在迁移期间与通用执行范围的映射必须明确；不得因引入新概念增加第二套独立的 Provider 执行队列或容量计数。

### 5.2 完成、异步及取消

- 同步调用正常逐层返回。
- 属于任务的异步子工作尚未结束时，即使入口返回“已受理”，Run 仍未完成。
- 独立后台任务、长期订阅及未来定时任务应建立新的执行范围并记录来源，不无限延长原 Run。
- 内核执行已声明的生命周期规则；模块决定任务如何编排、哪些错误可以处理以及怎样组织最终业务结果。
- 子调用失败不自动等于整个 Run 失败；必须保留原始子调用事实，即使父调用已处理错误。
- 取消请求、停止调度新子工作、进程实际停止和副作用是否完成是不同事实。未知停止不能当作释放容量的证据。
- 失败或取消不承诺撤销已完成的外部效果；补救由业务模块提供明确操作。
- 通用 Run 不是数据库事务，也不承诺跨模块原子执行或恰好一次外部副作用。

### 5.3 调用关系与数据依赖

父子 Call 表示谁调用谁；产出引用表示谁使用谁的结果。后续 Run 可以使用先前 Run 的产出，所以全局数据依赖不局限于一棵调用树，也不使旧 Run 重新进入运行状态。

## 6. Agent 使用通用调用机制

建议目标路径：

```text
Pi 扩展 → Agent 管理的进程通信 → Agent SDK 调用
       → 内核验证执行身份及授权上下文 → 统一模块路由 → 目标模块
```

Pi 与 Agent 仍需要进程通信。此通道只桥接 Provider 工具请求，不成为普通模块之间的第二套私有 RPC。传输方式由实现阶段选择。

迁移必须同时覆盖工具目录、执行、结果、取消和错误：

- 工具目录和实际执行使用一致的授权及选取范围。
- 保留原始调用者身份与 Agent 执行者身份，不把所有调用变成 Agent 自身身份。
- 保留预算、截止时间、审计、脱敏及未知停止约束。
- 并行或异步执行使用显式调用绑定，不依赖进程级可变的“当前上下文”。
- 不能仅因 SDK 接口已接通就删除旧入口；先证明新路径具备等价保证。
- 最终只有一份治理规则；若短期保留双入口，两者复用同一规则且必须有退场条件。

## 7. 返回结果与执行详情

建议统一结果外层协议，同时保持业务输出 Schema 的独立性。以下只是概念示例，不是当前 SDK 的新接口：

```json
{
  "result": { "total": 3250, "currency": "CNY" },
  "meta": {
    "status": "partial",
    "warnings": ["一个数据源读取失败"],
    "runId": "run_example",
    "callId": "call_example",
    "detailsRef": "detail_example"
  }
}
```

外层提供结果完整性、必要警告和查询入口，详细日志及大数据按引用读取，避免返回值随调用层数膨胀。旧调用者是否继续只收到业务结果，或通过显式选项读取外层协议，需要在接口冻结时决定。

详情查询独立鉴权：有权获得某个业务结果，不自动有权查看其全部原始资料、提示词或下游参数。保留可核验的输入、工具执行事实、输出及变更证据；模型生成的解释不能替代执行证据，也不要求记录或暴露模型内部推理。

## 8. 产出复用协议

下一次调用可以显式将已有产出绑定到特定输入位置。通用性意味着所有工具能通过公共协议明确接受、拒绝或声明不支持，而不是所有工具都能理解所有业务数据。

建议最小描述：

| 信息 | 用途 |
| --- | --- |
| 类型与版本 | 接收工具判断结构兼容性 |
| 数据或引用 | 提供实际输入，支持按需读取 |
| 产生者、Call/Run 关联及产生时间 | 追溯来源 |
| 适用范围、完整性、警告及可选有效期 | 判断是否满足本次业务要求 |
| 依据引用 | 核验来源及依赖 |

接收工具声明可接受的类型与版本，执行前验证结构和必要业务条件。不支持的必需输入应明确拒绝，不得静默忽略后报告成功。必要时显式调用转换模块，不默认自动转换或再次调用模型。

例如：账单工具产生账单集合，分析工具接受并生成报告，通知工具接受可展示报告。支付工具无需接受报告作为支付指令。

产出来源可验证不代表内容正确；引用不自动转移读取权限。产出被用于 Agent 输入时按数据处理，不提升为系统指令。优先使用不可变产出或明确版本，避免同一引用被修改后破坏历史依据；具体存储、保留期限和删除策略在产出阶段决定。

## 9. 内核、SDK 与模块边界

> 🧠 **From Hindsight memory (Conventions and patterns)** — 既有约定要求内核保持最小、模块通过路由交互，业务策略和结果组织优先留在模块。下表是针对本提案的职责建议，而非新增能力现状。

| 层 | 应承担职责 | 不应承担职责 |
| --- | --- | --- |
| 内核 | 可信身份、授权委托验证、调用路由、Call/Run 关联、预算、期限、必要队列与租约、取消及停止证据、最小执行记录 | 账单含义、报告组织、自动转换、业务补救及业务结果聚合 |
| 公共协议 | 调用和结果外层格式、产出描述、错误及版本契约 | 任意领域数据的统一语义 |
| SDK | `chrona.call` 门面、参数整理、类型辅助、上下文引用绑定、便捷输入输出处理 | 最终授权判断、独立可信身份或第二份生命周期真相 |
| Agent | Pi 及模型适配、工具注册桥接、操作控制与恢复、执行证据上报 | 任意提升原调用者权限、全系统业务会话与工作流 |
| 产出能力的拥有模块 | 内容保存读取、转换、来源查询和保留策略 | 绕过内核读取限制或自行赋予运行权限 |
| 编排/业务模块 | 工具选择、业务接受规则、流程、补救、结果汇总 | 自报可信身份、修改内核治理记录 |
| Web/MCP 等入口模块 | 用户交互、结果展示和受授权详情查询 | 独立复制调用治理规则 |

不因功能可复用就立即新增产出、工作流等模块；优先放到有真实职责的现有模块，出现多个实际消费者后再评估拆分。

`chrona.call` 不整体搬入内置模块：调用该模块本身仍需要可信调用机制；若它不可绕过并负责全局授权和生命周期，它就承担内核职责。可独立部署实现，但不能以模块命名代替信任边界设计。

## 10. 分阶段开发路线及验收

### P0：冻结最小契约与开发基线（建议下一步立即开展）

交付：实际调用路径清单、身份及授权规则、最小上下文契约、旧新接口映射、一个端到端样例及迁移计划。

必须决定：按工具声明及授予委托权限的方式、是否允许继续委托、上下文在异步/并发中的绑定、旧 `uses`/`visibility` 语义怎样保留或迁移、首阶段 Run 关联的最小需要。

验收：明确哪些检查由内核执行、哪些由工具执行；低权限服务合法调用高权限工具、工具向 Agent 委托必要权限、超范围请求被拒绝三种情形都能从契约直接判断。不得把“整个上下文任意合并”留给实现自行猜测。

### P1：通用调用上下文及 Agent 接入闭环

交付：可信上下文引用、必要授权委托、明确调用关联、Agent 使用统一工具目录及路由；保留旧有 Run 治理，暂不泛化整个工作流生命周期。

验收：真实 SDK 与受控 fake Pi 验证原调用者及授权来源不丢失、工具目录与执行一致、超范围拒绝、跨工作区引用拒绝、并发上下文不串用、超时及取消不突破原约束。队列边界重新验证失效授权；日志及错误不泄露令牌。

只有新路径通过这些验证，才退役专用入口中的重复治理。成功标准是治理统一，不能只以减少 HTTP 接口数量衡量。

### P2：有边界的通用 Run

交付：选定任务的入口、父子 Call、Run 生命周期、共享预算和取消传播；现有 Provider Run 映射与单队列治理保持清楚。

验收：同步完成、附属异步工作未结束、独立任务派生、已处理子错误、取消但未知停止、重试、进程重启均有确定行为。证明不会因重试刷新预算或重复执行不允许重放的副作用。

不强制所有查询都建立昂贵的持久化工作流；保留并定义必要的敏感内容不落盘规则。

### P3：可查询的结果与依据

交付：结果外层协议、必要警告、详情引用及受权限保护的查询能力。

验收：部分结果不会伪装成完整结果；用户或 Agent 能定位失败来源；无权限者无法沿引用读取原始敏感内容；不存在的、已删除的或过期详情有明确响应；普通业务数据消费不被破坏。

### P4：产出跨调用复用

交付：最小产出描述、输入绑定及接受/拒绝协议，先实现“资料读取 → 分析 → 通知”的受控流程。

验收：类型/版本不兼容、缺失必需数据、过期数据及读取未授权引用在副作用前被拒绝；接受的输入引用被记录；跨 Run 复用保留来源且不继承执行权限；转换必须显式。

### 后续按需求扩展

远端一般模块宿主、复杂工作流语言、自动类型转换、通用任意权限策略语言、任意历史任务自动重放不属于首轮范围。UI 可视化也不应阻塞调用契约与权限验证。

## 11. 实现前仍需解决的问题

1. 权限采用工具声明、调用时显式授予，还是二者结合？哪些能力允许委托，哪些必须由工具内部使用？
2. 发起人、直接调用者、执行者、授权来源如何分别记录，避免一个 caller 字段承担全部含义？
3. 同一模块同时处理多次调用时，SDK 如何安全绑定上下文，异步延续如何持久化？
4. 通用 Run 与现有 Run/ExecutionAttempt 是扩展、逻辑映射还是分层关系？如何保持唯一调度及容量真相？
5. 根调用返回、附属子工作完成与 Run 终态的精确规则是什么？
6. 授权失效、代码 hash 变化及重启后，排队工作和持久化上下文怎样重新验证？
7. 详情和产出引用由谁保存与回收？查询者能读到哪些字段，敏感内容何时完全不记录？
8. 新结果协议怎样保持现有工具输入输出消费行为？

这些问题不妨碍把本文作为路线讨论入口，但在 P1 修改持久化或授权机制前，应完成相关契约冻结。

## 12. 是否适合作为下一步开发路线

建议采用，条件是按 P0/P1 的范围启动，并以一个真实委托场景证明价值。

近期收益是减少 Agent 特殊路径、明确按工具授权和调用归属；中期收益是统一任务控制和执行核验；长期收益是产出在模块、Agent 及不同执行之间复用。

本路线不是部署许可，也不包含修改真实数据库、迁移用户数据或使用真实账号与模型。当前任务只整理文档，没有实施架构变更。开发验收使用临时数据、真实 SDK 进程和受控假后端；实际部署及数据迁移应另行制定可恢复方案。
